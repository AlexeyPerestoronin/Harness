# Phase 6. Client/Server implementation — базовое описание

> Документ описывает исходное состояние кодовой базы и целевое состояние после реализации клиент-серверного режима.
> Это первый документ пакета консультационного отчёта. Остальные части: `arch.md`, `tech.md`, `api.md`, `ui.md`, `auth.md`.

---

## 1. Назначение документа

Цель инициативы — реализовать клиент-серверное взаимодействие:

- серверная часть — `harness.exe`, запускаемый в режиме сервера по протоколу HTTPS;
- клиентская часть — `harness.wasm`, чистое Rust/Leptos web-приложение, работающее как самостоятельный клиент и как подключаемый модуль других Leptos WASM-приложений.

Документ фиксирует:

1. что уже есть в кодовой базе (`as-is`);
2. к чему мы хотим прийти (`to-be`);
3. ключевые архитектурные и технологические решения;
4. границы первой версии.

## 2. Исходное состояние (`as-is`)

### 2.1. Структура workspace

```
crates/
  conf/       # загрузка и валидация harness.json5 и файлов моделей
  logger/     # трейт Logger, DoubleLogger (stdout + файл), NullLogger
  tools/      # реестр инструментов: fs, git, terminal, user, skills, roles
  harness/    # бинарник: CLI, агентский цикл, HTTP-агенты, vendor-запросы
```

### 2.2. Основные компоненты

| Компонент | Расположение | Роль |
|---|---|---|
| CLI | `crates/harness/src/cli.rs`, `main.rs`, `help.txt` | Ручной парсинг аргументов, запуск сессии |
| Агентский цикл | `crates/harness/src/agent_loop.rs` | Итерации, лимиты, логирование, dump |
| Агенты | `crates/harness/src/agents/*` | xAI, Google, Claude, DeepSeek, AliBaba |
| Vendor HTTP | `crates/harness/src/vendor_request.rs` | Блокирующий `reqwest`, rate-limit, retry |
| Конфигурация | `crates/conf/src/*` | Загрузка `harness.json5`, моделей, сканирование каталога агентов |
| Инструменты | `crates/tools/src/*` | `fs`, `git`, `terminal`, `user`, `skills`, `roles` |
| Логгер | `crates/logger/src/*` | `Logger`, `DoubleLogger`, `NullLogger` |

### 2.3. Текущий пользовательский сценарий

1. Пользователь запускает `harness.exe --prompt "..." --conf harness.json5`.
2. CLI загружает конфигурацию; если `agent.config` — каталог, пользователь выбирает агента в консоли.
3. Если в модели нет API-ключа, ключ запрашивается в консоли.
4. Создаётся каталог сессии (`log.md`, `dump.json`).
5. `AgentLoop` синхронно выполняет итерации: запрос к вендору, вызов инструментов, логирование.

### 2.4. Ключевые ограничения для серверного режима

1. **Синхронный агентский цикл и блокирующий HTTP-клиент.**
   `AgentLoop::start` и `VendorRequest::send_json` выполняются в одном блокирующем потоке.
2. **Прямое обращение к stdin/stdout.**
   - `tools/user.rs` читает `stdin` для вопросов и подтверждений;
   - `agent_loop.rs::confirm` читает `stdin` для подтверждения превышения лимита;
   - `agent_select.rs::choose` читает `stdin` для выбора агента;
   - `main.rs::prompt_api_key` читает `stdin` для ввода API-ключа.
3. **Логгер не является событийной шиной.**
   Для web-клиента нужен механизм получения статуса и запросов на взаимодействие, а не только запись в файл/stdout.
4. **Нет примитива отмены.**
   Цикл нельзя остановить извне; блокирующий запрос к LLM нельзя прервать корректно.
5. **Выбор агента зашит в конфигурацию.**
   Список агентов умеет строить `conf::scan_agent_dir`, но публичного API для сервера нет.
6. **API-ключ запрашивается в консоли.**
   В серверном режиме это неприемлемо; ключ должен передаваться как обычный ответ пользователя через механизм взаимодействия.
7. **Один процесс — одна сессия.**
   Текущий `main` запускает ровно один `AgentLoop`; это поведение сохраняется и в серверном режиме.
8. **Нет аутентификации и TLS.**
   Текущая кодовая база не имеет ни серверного HTTP-слоя, ни механизма аутентификации, ни TLS-терминации.

## 3. Целевое состояние (`to-be`)

### 3.1. Сервер `harness.exe`

- `harness.exe` без параметров запускается в режиме HTTPS-сервера на порту по умолчанию.
- Поддерживаются параметры `--serve`, `--port`, `--host`, `--conf`, `--cwd`, `--auth-token`, `--tls-cert`, `--tls-key`.
- Сервер — это чистый API-сервер: только HTTPS + REST (JSON) поверх axum. Он **не содержит** web-интерфейса, не раздаёт статику и не использует иные протоколы (SSE, WebSocket и т.п. не применяются).
- Одновременно выполняется **не более одного** агентского цикла.
- Сервер автоматически завершается после простоя (`live-timeout`).
- Все эндпоинты `/api/v1/*`, кроме `GET /health`, требуют аутентификации по Bearer-токену, который передаётся **только** в заголовке `Authorization`.
- CORS по умолчанию запрещён; wildcard-режим `*` в первой версии не реализуется.
- Сервер предоставляет:
  - запуск/остановку цикла и передачу ответов пользователя;
  - проверку состояния запущенной сессии по персональному URL-hook (polling);
  - управление конфигурацией (`GET/PUT /api/v1/config`) — используется только встраиваемыми web-приложениями-плагинами;
  - файловое REST-API внутри `cwd` — используется только встраиваемыми web-приложениями-плагинами.
- Web-клиент **не получает** информации об агентах, API-ключах и логах сессии. Если серверу нужно выбрать агента или запросить API-ключ, он делает это через штатный механизм взаимодействия с пользователем; для клиента это выглядит как обычный запрос на ввод.

### 3.2. Клиент `harness.wasm`

- Чистое Rust/Leptos **CSR**-приложение, собираемое **Trunk**.
- Работает как самостоятельное приложение, публикуемое на GitHub Pages.
- Подключается к серверу по `https://localhost:<port>` или другому HTTPS-адресу.
- Умеет:
  - подключаться к серверу по адресу и Bearer-токену;
  - формировать промпт;
  - запускать и останавливать агентский цикл;
  - раз в 10 секунд опрашивать URL-hook сессии и отображать её состояние;
  - показывать запросы на взаимодействие (вопросы агента, выбор агента, ввод API-ключа) как обычное модальное окно и отправлять ответ;
  - показывать итоговый результат сессии.
- Клиент **не** знает про агентов и их API-ключи, **не** выбирает агента, **не** показывает лог сессии и **не** использует SSE.
- В первой версии standalone-клиент **не** работает с файловой системой и **не** редактирует `harness.json5`: среда настраивается локально на машине сервера.

### 3.3. Подключаемый модуль `web-harness`

- `web-harness` — Rust-крейт, подключаемый в родительское Leptos WASM-приложение через Cargo/Git.
- Экспортирует компоненту `HarnessPanel` и низкоуровневый `HarnessGateway`.
- Родительское приложение отображает панель в выделенной области своего интерфейса.
- Для встраиваемых приложений доступна **полноценная работа с файловой системой** через FS REST-API и клиентские компоненты `FsBrowser`/`ConfigEditor`, включаемые Cargo-фичей `fs-panel`.
- Динамическая runtime-загрузка `.wasm` в первой версии не используется. В будущем — переход на WIT/Component Model.

## 4. Ключевые решения

| Область | Решение |
|---|---|
| Серверный стек | **axum + tokio + async reqwest** — полностью асинхронный стек |
| Транспорт | **HTTPS + REST (JSON)**; только один протокол, polling каждые 10 секунд |
| TLS | TLS встроен в сервер; самоподписанный сертификат генерируется автоматически, либо используются пользовательские `--tls-cert`/`--tls-key` |
| Хранение TLS-артефактов | Каталог данных ОС вне `cwd` (Windows: `%LOCALAPPDATA%\harness\certs`); FS API не может их прочитать |
| Аутентификация | Bearer-токен только в заголовке `Authorization`; отдельный crate `auth`; middleware — единственный механизм защиты |
| CORS | По умолчанию запрещён; допускается только явный allowlist конкретных origin; `*` исключён |
| Клиент | **Leptos CSR**, сборка **Trunk** |
| Сессии | **Одна активная сессия**, без `SessionManager` |
| Статус сессии | `POST /run` возвращает клиенту `runUrl`; клиент опрашивает его каждые 10 секунд |
| Ввод/вывод | Единая зона ответственности: `Logger` + `Interaction` в crate `interactions`, реализации для CLI и Web |
| Выбор агента и API-ключ | Реализуются на стороне сервера через `Interaction`; web-клиент видит обычный запрос на ввод |
| Сетевой слой агента | Интерфейс `RequestPipeline` с pre/dur/post-действиями |
| Жизненный цикл сервера | `live-timeout`; сервер завершается после простоя; мутирующие API-вызовы продлевают таймер |
| Таймаут ввода | `server.interaction-timeout`, по умолчанию 10 минут; по истечении сессия завершается с ошибкой |
| Файловая система | FS API есть на сервере; standalone-клиент его не использует; работа с FS включается только в режиме плагина; действует deny-list и redaction |
| Интеграция в чужие приложения | Source-level Rust API через Cargo/Git |
| Сборка | `harness.exe` для Windows/Linux/macOS; `harness.wasm` на GitHub Pages |

## 5. Границы первой версии

1. Одна активная сессия на сервер.
2. Взаимодействие с агентом — текстовое (`input`/`output`); структурированные диалоги могут быть добавлены позже.
3. Остановка активного HTTP-запроса к вендору — мгновенная (за счёт async-отмены и `RequestPipeline`), но полная гарантия отмены зависит от поведения вендорного API.
4. Сервер работает только по HTTPS. Для локальной разработки используется самоподписанный сертификат; для удалённого доступа рекомендуется сертификат, выписанный доверенным УЦ, либо корпоративный PKI.
5. Аутентификация обязательна для всех `/api/v1/*`, кроме `GET /health`; токен передаётся только в заголовке.
6. CORS по умолчанию запрещён; `server.cors-allowed-origins` может содержать только конкретные origin.
7. Standalone `harness.wasm` не взаимодействует с файловой системой и не редактирует конфигурацию.
8. Удалённый запуск/скачивание `harness.exe` клиентом **не выполняется**. Если сервер недоступен, клиент показывает инструкцию пользователю.
9. Runtime-плагин (отдельный `.wasm` с динамической загрузкой) не реализуется.
10. Web-клиент не получает список агентов, не работает с API-ключами и не отображает лог сессии. Выбор агента и ввод API-ключа происходят как обычные запросы взаимодействия, инициируемые сервером.

## 6. Термины

| Термин | Значение |
|---|---|
| `cwd` | Корневая рабочая директория агентского цикла |
| `harness.json5` | Конфигурационный файл сервера/агентского цикла |
| Агентский цикл | Последовательность итераций: запрос к LLM → вызов инструментов → логирование → dump |
| REST | HTTP-протокол с JSON-запросами и ответами; единственный транспорт между клиентом и сервером |
| CSR | Client-Side Rendering, рендеринг на стороне браузера |
| `runUrl` / URL-hook | Персональный URL, возвращаемый при старте сессии и используемый клиентом для polling-проверки её состояния |
| Polling | Периодический опрос сервера клиентом; в первой версии интервал фиксирован — 10 секунд |
| `HarnessPanel` | Встраиваемая Leptos-компонента клиента |
| `HarnessGateway` | Транспортный слой клиента: REST + polling |
| `live-timeout` | Время простоя сервера, после которого он завершает работу |
| `interaction-timeout` | Максимальное время ожидания ответа пользователя на запрос взаимодействия |
| `pendingInput` | Активный запрос сервера на ввод пользователя (вопрос, выбор агента, API-ключ, подтверждение) |
| Redaction | Замена значений секретных полей (`api-key` и аналогичных) на `"***"` в ответах API |
| Deny-list | Список путей/файлов, к которым FS API запрещает доступ независимо от прав пользователя |
