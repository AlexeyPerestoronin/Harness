## 1. Резюме

Пакет №5 полностью отражает решения Project Owner, зафиксированные для пятой итерации в `WiKi/todo/phase-6/request.md`, и закрывает все блокеры предыдущего ревью пакета №4:

- **TLS-артефакты вынесены из `cwd`** в каталог данных ОС (`%LOCALAPPDATA%\harness\certs` на Windows, `$XDG_DATA_HOME`/`~/Library/Application Support` на Linux/macOS). FS API физически не может их прочитать (`base.md` §4; `arch.md` §8.2; `tech.md` §2.3).
- **Выбор агента и ввод API-ключа перенесены на сервер** и реализуются через `Interaction::input`. Web-клиент не имеет ни `AgentSelector`, ни `ApiKeyModal`, ни эндпоинтов `/agents` и `/crypto/*`; для клиента это обычный `pendingInput` (`base.md` §3.2; `arch.md` §9.2; `api.md` §3).
- **Лог сессии и SSE полностью убраны.** Транспорт — только HTTPS + REST (JSON). `POST /run` возвращает `runUrl`, который клиент опрашивает каждые 10 секунд; `GET /run/current` отдаёт статус, `pendingInput` и `result` (`base.md` §4; `api.md` §3; `tech.md` §4).
- **Б1 прошлого ревью (TLS-ключ в `cwd`)** закрыт: ключ вне `cwd` + deny-list `.harness/**` и секретоподобных файлов (`api.md` §5; `arch.md` §11.1).
- **Б2 прошлого ревью (контракт загрузки конфигурации без выбора агента)** закрыт: введены `load_server_config` и `resolve_agent_for_run`, `configState = ok` не зависит от выбора агента и наличия `api-key` (`arch.md` §9.1).
- **Б3 прошлого ревью (гонка SSE-replay)** снят удалением SSE как класса проблем: нет кольцевого буфера, broadcast-канала и `Last-Event-ID`; статус читается напрямую из `ActiveRun` (`arch.md` §8.3; `tech.md` §4.3).

Существенные замечания С1–С7 предыдущего ревью также закрыты:

- токен передаётся только в заголовке `Authorization`, query-параметры не принимаются (`auth.md` §1, §3.2);
- middleware `require_auth` — единственный механизм защиты, без дублирующего extractor'а (`auth.md` §3.2);
- открытый `GET /health` не раскрывает `cwd`, `port`, `liveTimeoutMinutes` (`api.md` §2);
- `live-timeout` сбрасывается мутирующими вызовами, поэтому длительное редактирование конфигурации/файлов не убивает сервер (`arch.md` §8.4);
- redaction/merge-правило ограничены разобранными JSON5/JSON с точным списком ключей, включая `tls-key` (`api.md` §5; `arch.md` §11.2);
- deny-list FS API защищает `harness.json5`, `.harness/**`, активные `log.md`/`dump.json` и секретоподобные файлы (`api.md` §5).

Архитектурное направление подтверждено и стало проще: axum + tokio + async reqwest, HTTPS REST + polling, Leptos CSR + Trunk, source-level интеграция `web-harness`, одна активная сессия, `RequestPipeline` с отменой. Каркас менять не нужно.

## 2. Что хорошо

1. **Все три решения Project Owner реализованы буквально и непротиворечиво.**
   - TLS-артефакты — в каталоге данных ОС вне `cwd`; FS API не может их прочитать (`base.md` §4; `arch.md` §8.2; `tech.md` §2.3).
   - Никакой клиентской логики агентов/ключей: нет `/agents`, `/crypto/*`, нет соответствующих UI-компонентов; выбор агента и ключ — серверные `pendingInput` (`base.md` §3.2; `api.md` §7; `ui.md` §3.7).
   - Лог/SSE убраны: только HTTPS REST, `runUrl` + polling 10 секунд (`base.md` §4; `tech.md` §1, §4; `api.md` §3).

2. **Архитектура упростилась ровно там, где это было нужно.**
   - Из `ServerState` исчезли `events_tx`, `EventRingBuffer`, RSA-ключи и хранилище зашифрованных ключей; остались `config`, `active`, `auth_token`, таймеры (`arch.md` §8.3).
   - `WebLogger`, `EventBus`, SSE-хендлер и replay-логика удалены; `WebInteraction` только сохраняет `pendingInput` и пишет файловый лог (`arch.md` §4, §5.1).
   - Роутер сократился до run/config/fs-эндпоинтов (`tech.md` §2.4; `api.md` §7).

3. **Контракт `conf` стал явным и покрывает дефолтный сценарий.**
   - `load_server_config` валидирует конфигурацию без выбора агента и без требования `api-key`.
   - `resolve_agent_for_run` выполняется только при `POST /run` и поддерживает `agent.config = file`/`directory`, автовыбор единственного кандидата и `api_key_override` (`arch.md` §9.1).
   - `api-key` запрашивается с `write_log = false`, чтобы не попасть в файл лога (`arch.md` §9.2; `tech.md` §7 п.6).

4. **Polling-контракт проработан корректно.**
   - `POST /run` возвращает `runUrl`; `GET /run/current` отдаёт `runState`, `summary`, `pendingInput` и `result` в нужных состояниях (`api.md` §3).
   - Терминальное состояние сохраняется до следующего `POST /run`, поэтому клиент не теряет результат при медленном polling (`arch.md` §8.4; `api.md` §3).
   - `pendingInput` имеет `requestId` (ULID с префиксом `req_`), `kind` (`text`/`confirm`), `prompt` и `timeoutAt` (`api.md` §3).
   - Для `kind = confirm` определена нормализация `y`/`n`; для `kind = text` пустой ответ отклоняется (`api.md` §3).

5. **Безопасность стала целостной.**
   - Токен только в заголовке `Authorization`; исключений для SSE нет, потому что SSE нет (`auth.md` §1, §4).
   - Deny-list закрывает `.harness/**`, `harness.json5`, активные `log.md`/`dump.json`, `.env`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa`, `id_ed25519` (`api.md` §5).
   - Redaction/merge — только для разобранных JSON5/JSON, по точному имени ключа, с `tls-key` в списке (`api.md` §5; `arch.md` §11.2).
   - Открытый `health` отдаёт только `status`, `version`, `serverTime`, `authRequired`, `runState`, `configState` (`api.md` §2).

6. **KISS/YAGNI соблюдены.**
   - Исключены SSE, WebSocket, RSA/Web Crypto на клиенте, `SessionManager`, runtime-плагины, Tailwind, query-токены, отдельный API логов.
   - `fs-panel` по-прежнему вынесен за Cargo-фичу, standalone-клиент остаётся минимальным (`tech.md` §5.3).
   - Выбор polling вместо SSE обоснован таблицей компромиссов (`tech.md` §4.1).

7. **Документы согласованы между собой.**
   - Термины `runUrl`, polling, `pendingInput`, deny-list, redaction последовательно определены (`base.md` §6).
   - Сводная таблица эндпоинтов `api.md` §7 совпадает с роутером `tech.md` §2.4.
   - Сигнатура `HarnessGateway::new(base_url, Option<String>)` зафиксирована и одинакова в `arch.md` §12.3, `auth.md` §5.2, `tech.md` §5.4.
   - Двухшаговый отказ `tools.user` (Deny → причина) явно сведён к обычной последовательности `pendingInput` (`ui.md` §3.6).

## 3. Что плохо

Критических ошибок и блокеров не выявлено. Остались четыре незначительные недоработки, которые стоит закрыть до или во время декомпозиции на задачи:

### Н1. Чувствительность поля ввода API-ключа определяется эвристикой на клиенте

`ui.md` §3.7 переключает `InputModal` в password-режим по наличию подстрок `"API-ключ"`/`"api-key"`/`"API key"` в `prompt`. Это хрупко: при другой локализации или нестандартном промпте сервера ключ будет вводиться в открытом текстовом поле, а клиент не имеет явного признака секретности.

**Почему это важно.** Решение PO требует, чтобы для клиента запрос ключа выглядел как обычный запрос на ввод, но это не запрещает серверу пометить запрос как секретный. Передача по HTTPS и `write_log = false` защищают канал и лог, однако визуальная маскировка ввода — дешёвая и ожидаемая мера.

**Рекомендация.** Добавить в DTO `pendingInput` булево поле `sensitive: bool` (или значение `kind = "secret"`), которое сервер выставляет при запросе API-ключа. UI по-прежнему использует один `InputModal`, но переключает тип поля на `password` по явному признаку, а не по подстроке.

### Н2. Контракт `resolve_agent_for_run` не моделирует состояние «требуется выбор»

`arch.md` §9.1 декларирует, что при `agent.config = directory` с несколькими кандидатами функция «возвращает запрос на выбор», но сигнатура `Result<ResolvedAgent, ConfError>` не показывает, как это состояние представлено, и как результат выбора передаётся в повторный вызов.

**Рекомендация.** Зафиксировать явное представление: например, `ConfError::AgentChoiceRequired(Vec<AgentCandidate>)` или отдельный enum-результат; описать последовательность «`resolve_agent_for_run` → `Interaction::input` → повторный `resolve_agent_for_run(agent_choice)`».

### Н3. Не определена валидация ответа при выборе агента

Для `kind = confirm` валидация ответа задана (`api.md` §3), а для выбора агента (пользователь вводит номер из промпта) поведение при некорректном номере не описано.

**Рекомендация.** Зафиксировать одно из двух: (а) сервер повторно выставляет `pendingInput` с тем же выбором; (б) сессия завершается с `failed` и понятной ошибкой в `result`. Это уберёт неоднозначность для реализатора и UI.

### Н4. Доступ к завершённым логам сессии через FS API не согласован с тезисом «лог не отдаётся через API»

`tech.md` §7 п.5 утверждает: «лог и dump сессии не отдаются через API». При этом deny-list в `api.md` §5 закрывает только **активные** `log.md`/`dump.json` (при `running`/`waiting_input`/`stopping`), а после завершения сессии эти файлы формально могут быть прочитаны через `GET /api/v1/fs/read` плагином с фичей `fs-panel`.

**Почему это важно.** Лог сессии может содержать чувствительные данные, прочитанные агентом. Если плагинам не нужен доступ к логам, это противоречие следует закрыть; если нужен — зафиксировать как осознанный риск.

**Рекомендация.** Либо добавить каталог логов сессий в deny-list FS API, либо явно написать, что завершённые логи доступны только локально/через `fs-panel` и это осознанное исключение.

## 5. Что можно улучшить

1. **Права на приватный ключ TLS.** Для Linux/macOS явно зафиксировать создание `key.pem` с правами `0600` и каталога с `0700`, чтобы ключ не читался другими локальными пользователями (`tech.md` §2.3).
2. **Нормализация `runUrl`.** В `tech.md` §5.4 зафиксировать, что `runUrl` всегда относительный и клиент обязан соединять его с `base_url` без повторного экранирования; это снизит риск open-redirect/ошибок конкатенации.
3. **Таймаут на стороне клиента.** В `ui.md` §3.5 интервал polling фиксирован (10 с), но не указан timeout отдельного `fetch`-запроса. Стоит задать его (например, ≤ 10 с), чтобы медленный/зависший запрос не накладывался на следующий polling-цикл.
4. **Повторный `POST /run` после терминального состояния.** Семантика уже корректна в `arch.md` §8.4, но в `api.md` §3 стоит явно добавить, что `409` возвращается только для `running`/`waiting_input`/`stopping`, а из `finished`/`failed`/`stopped` новый запуск допустим.
5. **Идентификация секретного промпта.** После введения `sensitive` (см. Н1) убрать из `ui.md` §3.7 эвристику по подстроке как основной механизм.
6. **Логирование факта ввода ключа.** Зафиксировать, что в файл лога при `write_log = false` не попадает ни промпт запроса ключа, ни сам ключ; тест на отсутствие `api-key` в `log.md` добавить в `tech.md` §9.
