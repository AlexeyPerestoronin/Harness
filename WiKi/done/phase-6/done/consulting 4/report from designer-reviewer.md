## 1. Резюме

Консультант корректно отработал решения Project Owner и замечания ревью пакета №3:

- HTTPS/TLS встроен в сервер (`axum-server` + `rustls`, `rcgen` для самоподписанного сертификата);
- CORS по умолчанию запрещён, добавлен отдельный crate `auth` с Bearer-токеном;
- введены redaction и merge-правило для секретов в `GET /config` и FS API;
- появился UI-компонент `ApiKeyModal` и полный сценарий RSA-передачи ключа;
- SSE-replay описан через кольцевой буфер + `Last-Event-ID` + `Event::id(...)`;
- у `web-harness` зафиксирован dual-layout (`lib.rs` + тонкий `main.rs`);
- добавлен `server.interaction-timeout` (по умолчанию 10 минут) и переход `WaitingInput → Failed`;
- отмена чтения тела вендорного ответа и `tokio::sync`-блокировки зафиксированы явно;
- поведение `GET /run/events` при отсутствии активного цикла определено.

Архитектурное направление остаётся жизнеспособным: axum + tokio + async reqwest, REST + SSE, Leptos CSR + Trunk, source-level интеграция `web-harness`, одна активная сессия, RSA-OAEP-256 для API-ключа. Менять каркас не нужно.

Тем не менее принимать пакет в текущем виде нельзя из-за трёх блокеров:

1. **Б1** — TLS-приватный ключ сохраняется внутри `cwd` и может быть прочитан через FS API.
2. **Б2** — не определён контракт загрузки серверной конфигурации без выбора агента; текущий `conf` API не покрывает сценарий `agent.config = directory`.
3. **Б3** — в примере SSE-хендлера есть гонка между чтением кольцевого буфера и подпиской на broadcast, из-за которой события могут теряться при переподключении.

## 3. Что плохо

### 3.1. Блокеры

#### Б1. TLS-приватный ключ сохраняется в `cwd` и доступен через FS API

- `arch.md` §8.1: *«сервер автоматически генерирует самоподписанный сертификат и сохраняет его в `cwd/.harness/certs/`»*.
- `tech.md` §2.3: *«`cert.pem()` / `signing_key.serialize_pem()` сохраняются в `cwd/.harness/certs/`»*.
- `api.md` §8: *«API работает со всем деревом `cwd`»*, а `GET /api/v1/fs/read` отдаёт содержимое любого текстового файла внутри `cwd`.
- Redaction в `api.md` §1/§8 покрывает только значения ключей `api-key`, `apikey`, `token`, `secret`, `private-key`. PEM-файл приватного ключа не является JSON-полем `private-key`; его содержимое — это `-----BEGIN PRIVATE KEY-----` и base64-тело, которые под правило redaction не подпадают.

**Почему это плохо.** `GET /api/v1/fs/read?path=.harness/certs/<key>.pem` вернёт приватный ключ TLS любому клиенту с Bearer-токеном. В сценарии встраиваемого плагина токен находится у родительского приложения; любая уязвимость/XSS в этом приложении или просто недобросовестный host-модуль получает ключ и может расшифровывать HTTPS-трафик сервера (MITM). Это прямо противоречит заявленному принципу `arch.md` §1: *«Секреты не покидают сервер. API-ключи и приватные ключи никогда не возвращаются клиенту»*.

**Как исправить.**
- Не хранить TLS-приватный ключ внутри `cwd`. Варианты:
  - хранить ключ в каталоге данных ОС вне `cwd` (например, `%LOCALAPPDATA%/harness/certs` на Windows) с ограничивающим ACL;
  - либо хранить только сертификат в `cwd/.harness/certs/`, а ключ — вне `cwd`;
  - либо не персистить ключ вообще, если допустимо пересоздание сертификата при каждом старте.
- Если ключ остаётся в `cwd`, обязательно добавить `.harness` (как минимум `.harness/certs`) в серверный deny-list FS API: чтение/запись/удаление этих путей возвращают `403`/`404`.
- Добавить тест: `GET /api/v1/fs/read` для `.harness/certs/*` не отдаёт PEM-приватный ключ.

***

Решение PO:

Хранить сертификаты в `%LOCALAPPDATA%`

#### Б2. Не определён контракт загрузки серверной конфигурации без выбора агента

- В текущей кодовой базе `harness.json5` содержит `"config": "C:/MyLife/Harness/harness/agents"` — то есть каталог агентов.
- Текущий `conf::load_with` при `agent.config = directory` требует `chooser`; `conf::load` возвращает ошибку `agent was not selected`.
- `arch.md` §8.2 определяет `LoadedServerConfig` со словами *«загруженные `Settings`, если конфигурация валидна»*. Но `Settings` в `conf` уже включает конкретного выбранного агента (`AgentSettings`).
- `api.md` §3 требует, чтобы сервер отдавал `GET /agents` до запуска, а `POST /run` получал `agentIndex`. Нигде не описан механизм: как сервер валидирует конфигурацию и считает `configState = ok` для directory-конфигурации, не выбирая агента на старте.
- Дополнительно: `apiKeyRequired` в `GET /agents` требует знания о наличии ключа у каждого кандидата, при этом текущий `scan_agent_dir` намеренно не читает `api-key`, а `load_model`/`resolve_api_key` падает при отсутствии `api-key`. Сервер же должен уметь запустить агента с ключом, переданным через RSA, даже если в файле агента ключа нет.

**Почему это плохо.** Для дефолтного сценария (`agent.config = directory`) реализатор не сможет корректно вычислить `configState` и список агентов, а `POST /run` с RSA-ключом может не пройти валидацию конфигурации. Это блокирует базовый пользовательский путь, заявленный в `base.md` и `ui.md`.

**Как исправить.** Явно зафиксировать в `arch.md`/`tech.md`/`base.md` расширение `conf`:
1. `load_server_config(conf_path)` — валидирует `cwd`, `server`, `tools`, `agent.mode`/лимиты и возвращает `ServerSettings` + список `AgentCandidate` **без выбора агента**; `configState = ok` не зависит от выбора агента.
2. `resolve_agent_by_index(index)` / `load_agent_by_index(index, api_key_override)` — дочитывает конкретный файл агента только при `POST /run`.
3. Загрузка модели должна допускать отсутствующий/пустой `api-key`, если передан `api_key_override` из RSA-хранилища; `apiKeyRequired` вычисляется как «нет ключа ни в файле модели, ни в RSA-хранилище вендора».
4. Описать поведение `GET /agents` для `agent.config = file` и `directory` отдельно, включая `source.kind`.

***

Решение PO:

Для первой реализации решено избавить от всей логики выбора агентов и ввода API-ключа.
Если на стороне сервера в harness.json5 не определена конкретная конфигурация, то будет запрос через модуль `Interactions` на который клиенте ответит в режиме обычного ответа.

Таким образом:
1. web-клиент не должен ничего знать ни про какие агенты и их API-ключи.
2. При запросе сервером выбора агента и/или ввода API-ключа, для web-клиента, это будет выглядеть как обычный запрос на взаимодействие с пользователем (т.е. никакой отдельной логики, никакого отдельного API).

#### Б3. Гонка в SSE-replay: события могут теряться между чтением кольцевого буфера и подпиской на broadcast

- В `tech.md` §4.4 хендлер сначала читает replay из `event_log` (кольцевой буфер), затем подписывается на `events_tx.subscribe()`.
- Агентский цикл в это время работает конкурентно: событие, опубликованное после снятия блокировки с `event_log`, но до создания подписки, не попадёт ни в replay, ни в live-канал.

**Почему это плохо.** Нарушается гарантия `api.md` §7: *«клиент передаёт `Last-Event-ID` … сервер сначала отправляет события с `id > Last-Event-ID`, затем live-поток»*. При переподключении можно потерять строку лога или, что хуже, `input_request`; тогда агентский цикл будет висеть в `waiting_input`, а клиент не покажет модальное окно до истечения `interaction-timeout`.

**Как исправить.** Зафиксировать корректный порядок:
- подписаться на broadcast до чтения replay;
- прочитать replay из кольцевого буфера;
- в live-цикле отбрасывать события с `id <= last_replayed_id`, чтобы не дублировать;
- либо держать `event_log` и подписку под одной блокировкой/последовательностью, гарантирующей отсутствие промежутка.
Обновить пример кода в `tech.md` §4.4 и sequence-диаграмму в `arch.md` §9.4.


***

Решение PO:

Отменяем решение о необходимости показывать лог сессии в web-клиенте:
- убираем SSE
- убираем всё API связанное с логом
- web-клиент не должен ничего знать о том, что на стороне клиента пишется какой-то лог.

При запуске агентской сессии сервер возвращает в ответе клиенту url-hook, по которому клиент может проверять статус сессии, наличие запросов на взаимодействие с пользователем и, если сессия, завершена результат. Web-клиент раз в 10 секунд проверяет статус своего запроса по hook, и на основании статуса ответа выполняет соответствующие действия: ожидает завершения, показывает запрос на взаимодействие, показывает результат по завершению.

Всё работает только по HTTPS через Axum (никаких других протоколов не использовать).

### 3.2. Существенные замечания

#### С1. Противоречие в описании «токен в URL» для SSE

`auth.md` §4 разрешает для `GET /run/events` передавать токен query-параметром `?auth_token=<token>`, потому что `EventSource` не поддерживает заголовок `Authorization`. При этом `auth.md` §7 в таблице угроз утверждает: *«Токен передан в URL и попал в логи/историю | Не используется: токен передаётся только в заголовке»*. Это прямое противоречие.

**Почему это плохо.** Документ сам себя опровергает, и реализатор может ошибочно считать, что токен в URL не используется. Реальный токен в query-строке может попасть в логи reverse-proxy/историю браузера; это осознанный компромисс, но он должен быть честно описан.

**Как исправить.** Сделать основным механизмом короткоживущий `sse_ticket`: клиент получает его REST-запросом с Bearer-заголовком и передаёт в `?ticket=...` только для SSE. `?auth_token=` оставить как явно задокументированный fallback с предупреждением. Обновить таблицу угроз в `auth.md` §7.

#### С2. FS API не защищает критически важные файлы сервера

`api.md` §8 разрешает `DELETE /fs/remove` и `PUT /fs/write` по всему `cwd`. Нет серверного запрета на удаление/перезапись `harness.json5`, `.harness`, активного `log.md`/`dump.json`. В UI есть подтверждение (`ui.md` §3.9), но защита только на клиенте недостаточна: встраиваемый host-модуль может вызвать API напрямую.

**Почему это плохо.** Плагин с токеном (или XSS в нём) может удалить конфигурацию сервера, TLS-артефакты, логи текущего цикла или файлы ролей/навыков. Для сервера, который по сути является точкой выполнения агентского цикла, это опасно.

**Как исправить.** Ввести серверный deny-list/защиту: `.harness/**` — полностью недоступно; `harness.json5` и файлы активного цикла (лог, dump) — нельзя удалять/перезаписывать во время `running`/`waiting_input`/`stopping`. Возвращать `409`/`403` с понятным кодом ошибки. Добавить тесты.

#### С3. `live-timeout` конфликтует со сценарием длительного редактирования файлов через `fs-panel`

`arch.md` §8.3 фиксирует, что polling-запросы не продлевают `live-timeout`; таймер перезапускается только после завершения цикла. При этом для встраиваемых приложений включена полноценная работа с FS (`ConfigEditor`, `FsBrowser`, `ui.md` §3.8–3.9). Пользователь, редактирующий `harness.json5` или файлы ролей дольше `live-timeout` (по умолчанию 5 минут), потеряет сервер.

**Почему это плохо.** Получается UX-ловушка: длинная правка конфигурации без запуска цикла приводит к закрытию сервера, после чего плагин теряет состояние и не может сохранить изменения.

**Как исправить.** Принять одно из решений и зафиксировать его: (а) приостанавливать/сбрасывать `live-timeout` при мутирующих `PUT /config` и FS-операциях (или при открытом SSE-соединении); (б) если оставить строгое поведение «жизнь сервера продлевает только запуск цикла» — явно показывать в `fs-panel` таймер до остановки и предупреждать перед сохранением. Первый вариант лучше соответствует заявленной работе с FS у плагинов.

#### С4. Открытый `GET /health` раскрывает `cwd` и `port`

`api.md` §2 возвращает `cwd`, `port`, `liveTimeoutMinutes` без аутентификации. Для удалённого доступа (`--host 0.0.0.0`) это означает, что любой может узнать внутренние пути и порт сервера без токена.

**Почему это плохо.** Информационное раскрытие: `cwd` может содержать имя пользователя/структуру каталогов, а связка `cwd` + `port` упрощает атаки. Для локального bind это не критично, но для удалённого — нежелательно.

**Как исправить.** Оставить в открытом `health` только `status`, `version`, `serverTime`, `authRequired`, `runState`, `configState`. `cwd`, `port`, `liveTimeoutMinutes` перенести в аутентифицированные `GET /run` или `GET /config`.

#### С5. Redaction/merge для произвольных текстовых файлов недоопределён

`api.md` §8 декларирует: *«Секретные поля в текстовых файлах подлежат redaction на чтении и merge-правилу на записи»*. Но все примеры — только JSON5/JSON. Для произвольного текста (PEM, `.env`, YAML, код) неясно, как искать «секретные поля», не испортив файл и не пропустив варианты (`api_key`, `API-KEY`, `apiKey`, substring `token` и т.п.).

**Почему это плохо.** Текстовая редкация по подстрокам может испортить не-JSON файлы (например, `tokenLimit` в коде) или пропустить реальные секреты. Это одновременно риск целостности и ложное чувство безопасности.

**Как исправить.** Ограничить гарантированную redaction/merge разобранными JSON5/JSON-файлами с точным списком ключей и семантикой «точное имя ключа, не substring». Для остальных текстовых файлов либо отдавать как есть, либо явно запретить чтение файлов, похожих на секретные (PEM/`.env`), либо ввести явный список масок. Зафиксировать поддерживаемые форматы и тесты.

#### С6. Непротиворечивость CORS для `EventSource` и заголовка `Last-Event-ID`

`api.md` §1 разрешает preflight-заголовки `Authorization, Content-Type`. Браузерный `EventSource` при переподключении автоматически отправляет заголовок `Last-Event-ID`. Для cross-origin SSE этот заголовок не является CORS-safelisted, и при определённой политике preflight соединение может быть заблокировано, если `Last-Event-ID` не включён в `Access-Control-Allow-Headers`.

**Почему это плохо.** Заявленный механизм переподключения (`Last-Event-ID`) может не работать именно в cross-origin сценарии GitHub Pages → localhost, ради которого всё проектировалось.

**Как исправить.** Проверить поведение целевых браузеров и, при необходимости, включить `Last-Event-ID` в `Access-Control-Allow-Headers` для SSE-маршрута (или явно задокументировать, почему это не требуется). Добавить CORS-тест с `Origin: <allowed>` и `Last-Event-ID`.

#### С7. Дублирование механизмов аутентификации: middleware и extractor

`auth.md` §3.2 описывает axum-экстрактор `AuthUser` (`FromRequestParts`), а §4 — middleware `auth::require_auth`, который навешивается на весь protected-роутер. Неясно, что из этого канонический механизм; если применить оба, проверка выполнится дважды, а SSE-маршрут всё равно потребует отдельной логики query-токена.

**Почему это плохо.** Неоднозначность для реализатора, возможный двойной слой и расхождение в обработке ошибок.

**Как исправить.** Зафиксировать middleware как единственный канонический механизм защиты маршрутов; экстрактор либо удалить, либо пометить как внутреннюю деталь. Явно описать, как middleware различает `Authorization` для REST и `?ticket`/`?auth_token` для SSE.

## 5. Что можно улучшить

1. **Синхронизировать сигнатуру `HarnessGateway::new`.** В `arch.md` §12.3 передаётся `auth_token` строкой, в `auth.md` §5.2 — `Option<String>`. Зафиксировать один вариант (лучше `Option<String>`/`impl Into<Option<String>>`) и использовать во всех примерах.

2. **Уточнить `GET /api/v1/agents` при ошибках.** `api.md` §3 пишет *«409/412»*; следует разделить: `412` — конфигурация отсутствует/невалидна, `409` — конфигурация валидна, но нет ни одного кандидата.

3. **Явно описать двухшаговый отказ в `tools.user` для web.** Текущий `request_*_access_for` после `n` запрашивает «Причина отказа». В `ui.md` §3.6 это не отражено; реализатору стоит зафиксировать, что после Deny сервер пришлёт второй `input_request`, и UI должен корректно открыть следующее модальное окно.

4. **Уточнить redaction для `server.tls-key` в конфигурации.** Список секретных ключей (`api-key`, `apikey`, `token`, `secret`, `private-key`) не включает `tls-key`, который указывает на приватный ключ TLS. Решить, скрывать ли его значение (путь) в `GET /config`.

5. **Добавить тесты на redaction TLS-артефактов и deny-list FS API** — отдельно от тестов на `api-key`.

6. **Продумать утечку секретов через `GET /run/log` и `GET /run/dump`.** Логи и dump-файлы могут содержать чувствительные данные (если агент читал секретный файл или писал ключ). В первой версии можно принять это как осознанный риск, но его стоит зафиксировать в `base.md`/`api.md`, а не оставлять неявным.

7. **Доработать пример `EventSource → Stream` в `tech.md` §5.4.** Текущий код не обрабатывает `onerror`, не закрывает `mpsc` и утекает `Closure`. Для плана задач достаточно сослаться на канал + `Closure`, но нужно явно указать, что reconnect/cleanup — часть реализации, а не оставить код как production-образец.

8. **Зафиксировать формат `requestId`.** Сейчас пример `req_01J...` выглядит как ULID; если важна сортировка/уникальность, указать источник (`uuid`/ULID) и длину.

9. **Уточнить поведение `POST /run/input` с пустым ответом.** Допустим ли `answer: ""`? В CLI пустая строка допустима; в web UI textarea может быть пустой. Зафиксировать валидацию.

10. **Подумать о деплое `web-harness` как крейта.** `tech.md` §9 упоминает `cargo package`/crates.io; стоит явно зафиксировать, публикуется ли он на crates.io или только git-tag, чтобы host-приложения знали источник.

## 6. Итоговый вердикт

**Отправить на доработку Project Consultant.**

Концептуальное направление утверждается: axum + tokio + async reqwest, HTTPS + REST + SSE, Leptos CSR + Trunk, source-level интеграция, одна активная сессия, RSA-передача API-ключа, redaction секретов. Каркас менять не нужно, пакет №4 уже близок к готовности для декомпозиции на задачи.

Перед началом планирования задач необходимо закрыть три блокера:

1. **Б1** — исключить возможность чтения TLS-приватного ключа через FS API (вынести ключ из `cwd` или закрыть `.harness` deny-list'ом).
2. **Б2** — описать контракты `conf` для загрузки серверной конфигурации без выбора агента, отложенного выбора агента по `agentIndex` и запуска с RSA-ключом.
3. **Б3** — исправить гонку в SSE-replay (subscribe → replay → dedupe) и обновить пример кода/диаграмму.

Существенные замечания С1–С7 также должны быть отражены в документах до декомпозиции, но они не отменяют выбранную архитектуру. Альтернативный архитектурный путь не требуется.
