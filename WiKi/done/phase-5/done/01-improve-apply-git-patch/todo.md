# Задача на разработку: Улучшить сообщение об ошибке `apply_git_patch`

Добавить в сообщение об ошибке инструмента `apply_git_patch` подробную справку о том, как именно должен формироваться каждый `*.patch`, с 2–3 короткими примерами. Справка должна возвращаться в составе ошибки только один раз за сессию агентского цикла.

Зачем: сейчас при некорректном patch модель получает только короткое сообщение `invalid or empty patch format` либо сырой вывод `git apply`, не понимает требуемый формат и повторяет ошибку, расходуя итерации и токены.

Ожидаемый результат: первый провал `apply_git_patch` в рамках одной сессии возвращает ошибку с подробной справкой и примерами; все последующие провалы в той же сессии возвращают короткую ошибку без повторения справки.

## Функциональные требования

1. Логика самого инструмента остаётся прежней:
   - пустой/состоящий только из пробелов patch отклоняется;
   - из patch извлекаются целевые пути (`extract_patch_target_paths`);
   - для каждого пути проверяется доступ на запись через sandbox;
   - patch записывается во временный `harness-<seq>.patch` в `temp-dir`;
   - выполняется `git apply --ignore-whitespace --ignore-space-change --recount <tmp-file>`.

2. В `crates/tools/src/git.rs` добавить состояние «справка уже показывалась в этой сессии». Подойдёт, например, `AtomicBool` в `GitModule`, инициализируемый значением `false`. `GitModule` создаётся один раз на сессию (`ToolRegistry::build` вызывается в `AgentLoop::new`), поэтому время жизни этого флага совпадает с сессией.

3. Добавить константу/функцию с текстом справки (далее — `PATCH_FORMAT_HELP`). Справка должна объяснять:
   - `*.patch` — это unified diff / git-style patch;
   - обязательны заголовки `---`/`+++` и/или `diff --git` с путями `a/...` и `b/...`;
   - обязателен hunk-заголовок вида `@@ -<start>,<count> +<start>,<count> @@`;
   - строки изменений должны иметь префиксы `+` / `-` / пробел, вокруг patch не должно быть пояснительного текста;
   - один файл patch — это минимально допустимый случай.

4. В справке привести 2–3 коротких примера. Примеры должны быть реально применимыми с текущей командой `git apply`. Допустимый набор примеров:
   - однофайловый patch через `---`/`+++`:
     ```
     --- a/README.md
     +++ b/README.md
     @@ -1,1 +1,1 @@
     -old line
     +new line
     ```
   - однофайловый patch через `diff --git`:
     ```
     diff --git a/src/main.rs b/src/main.rs
     index 1111111..2222222 100644
     --- a/src/main.rs
     +++ b/src/main.rs
     @@ -1,3 +1,3 @@
      fn main() {
     -    println!("hi");
     +    println!("hello");
      }
     ```
   - двухфайловый patch:
     ```
     diff --git a/a.txt b/a.txt
     --- a/a.txt
     +++ b/a.txt
     @@ -1 +1 @@
     -a
     +A
     diff --git a/b.txt b/b.txt
     --- a/b.txt
     +++ b/b.txt
     @@ -1 +1 @@
     -b
     +B
     ```

5. При любой ошибке `apply_diff_patch` (невалидный/пустой patch, отказ sandbox, ошибка `git apply`) возвращать:
   - первый раз в сессии: `cannot apply diff patch → <текущая причина ошибки>\n\n<текст PATCH_FORMAT_HELP>`;
   - последующие разы в той же сессии: `cannot apply diff patch → <текущая причина ошибки>` без справки.

6. Справка не должна выводиться в лог отдельной записью и не должна добавляться к успешным ответам инструмента.

## Проверка корректности решения

- `cargo check --workspace` выполняется без ошибок.
- `cargo test --workspace` выполняется без ошибок.
- Если добавляются юнит-тесты, покрыть ими:
  - первый вызов с невалидным patch возвращает текст справки;
  - второй вызов в том же `GitModule` не содержит текста справки.
- Ручная проверка: запустить сессию с включённым `tools.git`, дважды вызвать `apply_diff_patch` с заведомо битым patch и убедиться, что справка пришла только в первой ошибке.
