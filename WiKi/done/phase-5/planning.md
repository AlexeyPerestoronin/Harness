# Задачи для V фазы разработки

## Improve apply_git_patch
Добавить в сообщение об ошибке для `apply_git_patch` подробную информацию о том, как именно должен формироваться каждый `*.patch` c приведением 2-3 коротких примеров.
Данная сообщение должно выводиться в качестве ошибки единожды на сессию, чтобы не дублировать большой массив одинаковой информации каждый раз при падении.

1. Полностью удалить `run_invoke` (без обратной совместимости).
2. Полностью удалить `list_available_shell_commands` (без обратной совместимости).
3. Расширить описание команды `run_shell` добавив информацию о списке доступных команд и доступных `cwd`.

## Improve CLI
1. Добавить опциональный параметр `--cwd <path>` который буде задавать корневую рабочую директорию для агентского цикла:
    - `--cwd <path>` имеет наивысший приоритет
    - отдельно отмечу, что:
      - CWD в любом из способов может быть задан как относительный путь (например `"cwd": "."` или `--cwd .`), относительно рабочего файла конфигурации;
      - необходимо удостовериться, что логика работы агентского цикла не выходит за пределы CWD никоем образом (все файловые операции происходят внутри CWD включая невозможность выйти за пределы используя относительные пути вроде `../../../`) и, если это не так, то поправить в рамках отдельной задачи.

2. Добавить опциональный параметр `--api-key <key>` который будет задавать API-ключ для текущего агентского цикла:
    - `--api-key <key>` имеет наивысший приоритет относительно других способов получения ключа;
    - в качестве `<key>` должна быть возможность ввода как самого ключа так и пути до файла относительно CWD где он записан (подобно тому, как это работает для конфигурационных файлов агентов).

## Allow getting API via console
Все настройках для агентов необходимо разрешить ключу `api-key` быть пустым (сейчас там может быть записан либо собственно ключ, либо путь до файла где он записан).
В случае, если `api-key` пустой и не передан через CLI, просить пользователя ввести ключ в консоли.

## Very long thinking
В некоторых запросах, умные модели (Grok-4.6, DeppSeek-4-Pro, CloudSonnet-5.5) могут очень долго отвечать на очередной request в виду долгого цикла внутренних рассуждений (больше 2 минут), что по итогу приводит к тому, что ожидание ответа падает по timeout.

Пример:
```md
## Iteration №15
Usage:
- time = 3 min 24 sec
- tokens = 63918
- USD approximated = 0.31
- USD real = 0.38
⚠️ 1-attempt request failed: error sending request for url (https://api.x.ai/v1/chat/completions)
⚠️ 2-attempt request failed: error sending request for url (https://api.x.ai/v1/chat/completions)
⚠️ 3-attempt request failed: error sending request for url (https://api.x.ai/v1/chat/completions)
⚠️ 4-attempt request failed: error sending request for url (https://api.x.ai/v1/chat/completions)
```

Подобное поведение приводит к тому, что harness разрывает соединение так и не дождавшись ответа, повторяет попытку, которая вновь выполняется очень долго, что по итогу приводит к зацикливанию запросов и бессмысленному потреблению токенов.

Такое поведение необходимо исправить:
- ответ за запрос может ожидаться бесконечно долго
- только пользователь может завершить ожидание ответа явным прерыванием процесса агентского цикла
- процесс ожидания должен быть асинхронным и наблюдаемым для пользователя → пусть в консоли во время ожидания ответа постоянно обновляется секундомер: `response waiting time: 1 min 40 sec`
  - в логах этот секундомер фигурировать не должен
  - секундомер должен обновлять значение в консоли каждую секунду
  - чтобы консольный вывод не засорялся, необходимо перезаписывать последнюю строку
