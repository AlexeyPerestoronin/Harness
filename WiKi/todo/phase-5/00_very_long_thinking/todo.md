# Задача на разработку: Very long thinking — бесконечное ожидание ответа модели с консольным секундомером

В `crates/harness/src/vendor_request.rs` убрать 300-секундный HTTP-таймаут (`CLIENT_TIMEOUT`) и перевести фактическое выполнение каждого HTTP-запроса модели в отдельный поток. Пока запрос выполняется, агентский цикл должен каждую секунду обновлять в консоли одну и ту же строку `response waiting time: X min Y sec`; в файл лога (`log.md`) этот секундомер попадать не должен.

Зачем: сейчас `reqwest` обрывает запрос по `CLIENT_TIMEOUT` (300 секунд). Умные модели (Grok-4.6, DeepSeek-4-Pro, ClaudeSonnet-5.5 и т.п.) могут думать дольше 2 минут, из-за чего запрос падает с `error sending request for url`, harness повторяет попытку, которая снова выполняется долго, и цикл бессмысленно расходует токены. Ожидание ответа должно быть бесконечным, а пользователь должен видеть, что процесс жив, и мог прервать его вручную.

Ожидаемый результат:
- HTTP-клиент не имеет таймаута ожидания ответа и может ждать ответ сколь угодно долго.
- В консоли во время ожидания ответа раз в секунду обновляется одна строка `response waiting time: X min Y sec`; в `log.md` она не появляется.
- Прервать ожидание может только пользователь явным прерыванием процесса агентского цикла (Ctrl+C / завершение процесса).

## Функциональные требования

### 1. Убрать таймаут HTTP-клиента

- В `crates/harness/src/vendor_request.rs` удалить константу `CLIENT_TIMEOUT` и её doc-комментарий.
- Убрать вызов `.timeout(CLIENT_TIMEOUT)` из `Client::builder()` в `VendorRequest::new_with_clock`.
- Не устанавливать вместо него `connect_timeout` / `read_timeout` / `timeout`. Результирующий `reqwest::blocking::Client` должен ждать ответ бесконечно; при необходимости явно убедиться по документации reqwest, что ни один из этих параметров не ограничивает запрос.
- Оставить без изменений:
  - `MAX_ATTEMPTS` и ретрай-цикл;
  - `RateLimit` и ожидания rpm/tpm/rpd;
  - классификацию `RetryAction` (429 → `WaitAndRetry`, 503 → `SleepRandomAndRetry`, 2xx → `Success`, остальные → `Fail`);
  - логирование `⚠️ {attempt}-attempt request failed: {e}` и сообщений 429/503.

### 2. Асинхронное ожидание HTTP-запроса

- В `VendorRequest::execute` изменить непосредственный вызов `send_once()`:
  - сигнатура closure должна допускать отправку в другой поток: `F: FnMut() -> Result<(u16, String), String> + Send` (текущий closure из `send_json` этому условию удовлетворяет);
  - выполнять `send_once` в отдельном потоке через `std::thread::scope`, чтобы поток агентского цикла не блокировался и мог обновлять секундомер;
  - результат передавать из потока через `std::sync::mpsc::channel`, а ожидать через `rx.recv_timeout(Duration::from_secs(1))`.
- Scoped-поток должен заимствовать `send_once` без требования `'static`, чтобы после завершения попытки тот же `FnMut`-closure можно было использовать для следующей попытки ретрай-цикла.
- Если канал закрылся, а результат так и не был отправлен (поток завершился, не отправив ответ), вернуть из хелпера ошибку `response waiting thread failed`; в `execute` она обрабатывается как обычная транспортная ошибка попытки: логируется `⚠️ {attempt}-attempt request failed: response waiting thread failed`, после чего попытка повторяется по общему ретрай-циклу.

### 3. Консольный секундомер

- Ввести приватный хелпер вида:

  ```rust
  fn format_waiting_time(secs: u64) -> String {
      format!("{} min {} sec", secs / 60, secs % 60)
  }
  ```

- На каждый `RecvTimeoutError::Timeout` (то есть раз в секунду) печатать в stdout строку:

  `response waiting time: {format_waiting_time(elapsed_secs)}`

- Правила вывода секундомера:
  - секундомер пишется напрямую в stdout (`print!` + `std::io::stdout().flush()`), **не** через `Logger`, поэтому в `log.md` он не попадает;
  - первый вывод секундомера в рамках одной попытки начинается с `\n`, чтобы не затереть последнюю строку лога; последующие выводы начинаются с `\r` и перезаписывают строку секундомера;
  - если новая строка короче предыдущей, она дополняется пробелами до длины предыдущей строки, чтобы на консоли не оставались «хвосты» от более длинного значения;
  - если результат пришёл быстрее чем за 1 секунду, секундомер не печатается;
  - после получения результата финальная строка секундомера остаётся в консоли; последующие записи `DoubleLogger` начинаются с `\n` и продолжаются с новой строки.
- Секундомер запускается заново для каждой HTTP-попытки (`send_once`) внутри `execute`. Ожидания rate-limit и sleep-бэкоффы 429/503 в секундомер не входят.

### 4. Логирование

- Все существующие сообщения `VendorRequest` (`⚠️ {attempt}-attempt request failed: ...`, ` fail 429: model limit exceeded!`, ` fail 503: waiting ...`) должны по-прежнему писаться через `self.logger` и попадать и в консоль, и в `log.md`.
- Ни одно сообщение секундомера не должно вызывать `Logger::log_str` / `Logger::log_line`.

## Проверка корректности решения

- `cargo check --workspace` выполняется без ошибок.
- `cargo test --workspace` выполняется без ошибок.
- Поиск по репозиторию не находит `CLIENT_TIMEOUT`.
- Юнит-тесты в `vendor_request.rs`:
  - `format_waiting_time(1) == "0 min 1 sec"`;
  - `format_waiting_time(59) == "0 min 59 sec"`;
  - `format_waiting_time(60) == "1 min 0 sec"`;
  - `format_waiting_time(100) == "1 min 40 sec"`;
  - `execute` с немедленным `Ok((200, "ok".into()))` возвращает `Ok("ok")` и не печатает секундомер;
  - `execute` с первой попыткой `Err("boom")` и второй `Ok((200, "ok"))` возвращает `Ok("ok")`;
  - `execute` с `Ok((400, "bad"))` возвращает `Err("HTTP 400: bad")`.

  Для тестов использовать `NullLogger` и fake-`Clock` с `rpm = -1`, `tpm = -1`, `rpd = -1`, чтобы не было реальных ожиданий.

- Ручная проверка:
  - запустить сессию с любым реальным агентом; после первой секунды ожидания в консоли появляется и обновляется одна строка `response waiting time: ...`, при этом предыдущие строки лога не затираются;
  - после ответа модели финальная строка секундомера остаётся в консоли, а следующие записи лога идут с новой строки;
  - в `log.md` сессии строка `response waiting time` отсутствует;
  - во время ожидания нажать Ctrl+C — процесс агентского цикла завершается;
  - при медленном ответе модели (дольше 2 минут) ошибка `error sending request for url` по таймауту не возникает.
