# Задача на разработку: Запуск harness как HTTP-сервера
Добавить режим сервера: тот же `harness.exe` и тот же `harness.json5`, но сессии запускаются по HTTP, а не только через `--prompt` / `--dump`.

Зачем: сейчас бинарь — одноразовый CLI (`--prompt` xor `--dump` xor `--conf-new`). Нужна возможность держать процесс и принимать запросы на сессию.

Ожидаемый результат: `harness.exe [--conf <path>] --server [--host <addr>] [--port <n>]` слушает HTTP, обрабатывает сессии тем же `AgentLoop`, что CLI, и не ломает существующие флаги.

## Функциональные требования
### 1. CLI
1. Новый флаг `--server`. Опционально:
   - `--host <addr>` — default `127.0.0.1` (не `0.0.0.0`: не торчать наружу без явного указания);
   - `--port <n>` — default `8080`.
2. `--server` взаимоисключающий с `--prompt`, `--dump`, `--conf-new` (расширить текущее xor-правило). Один из `--prompt` / `--dump` / `--conf-new` / `--server` обязателен.
3. `--conf` с `--server` разрешён; без `--conf` — default `<process-cwd>/harness.json5`, как сейчас.
4. `--help` / `crates/harness/help.txt` описать новые флаги и xor-правило. Тесты `crates/harness/src/cli.rs` обновить.
5. Парсер по-прежнему без clap.

### 2. Поведение сервера
1. После разбора CLI загрузить conf **один раз**, затем слушать `host:port` блокирующе. Async runtime (tokio и т.п.) не вводить. HTTP — `std::net::TcpListener` + разбор минимального HTTP/1.1 **либо** маленький blocking crate (`tiny_http`). Не тянуть axum/warp/hyper-async.
2. Конкурентность: **одна сессия одновременно**. Пока идёт loop — следующий запрос ждёт (очередь на accept/обработку). Не пул агентов.
3. Каждая успешная сессия создаёт **новый** session dir через существующий `session_dir` (как CLI `--prompt`), пишет `log.md` и `dump.json`.
4. Инструменты, лимиты, агент — из загруженного conf, без отдельных server-настроек в json5.

### 3. HTTP API (минимальный)
**`GET /health`**
- `200`, body `ok` (text/plain) или `{"ok":true}`. Без conf-побочек.

**`POST /run`**
- `Content-Type: application/json`
- Body — объект:
  - `{ "prompt": "<text>" }` — новая сессия, аналог `--prompt`;
  - `{ "dump": "<path>" }` — продолжение из dump, аналог `--dump`;
  - оба поля сразу или ни одного — `400`.
- Успех `200` JSON:
  ```
  { "ok": true, "log_dir": "<absolute path of session dir>" }
  ```
  Не обязательно возвращать полный текст агента: он уже в `log.md`.
- Ошибка валидации / неизвестный path — `400` с `{ "ok": false, "error": "..." }`.
- Ошибка loop/агента — `500` с `{ "ok": false, "error": "..." }`. Процесс при этом **не** завершать.
- Прочие path / методы — `404` / `405`.

### 4. Интерактивные инструменты
`ask_user` / `request_*` читают stdin. В server-режиме stdin не является консолью оператора запроса.
- Не переписывать `user` модуль на HTTP handshake.
- Если такой инструмент вызван во время server-сессии, допустимо вернуть tool-error «interactive user tools are not available in server mode» **либо** оставить блокирующий stdin (как CLI) — но тогда это должно быть явно написано в README. Предпочтительный минимальный вариант: не менять user.rs в этой задаче (блокирующий stdin), и в README одной фразой предупредить, что interactive tools в `--server` не предназначены для удалённого клиента.

### 5. Останов
SIGINT/Ctrl+C — обычное завершение процесса. Отдельный `/shutdown` не нужен.

## Проверка корректности решения
1. `cargo test --workspace` (cli xor, help содержит `--server`).
2. Ручная проверка без реального агента по возможности: `GET /health` после `--server` с валидным conf. Если для `/run` нужен живой API key — не ходить в сеть; достаточно unit-теста разбора body (`prompt` xor `dump`) и cli-тестов.
3. Старые сценарии: `--prompt` / `--dump` / `--conf-new` / `--help` не изменились по смыслу.
