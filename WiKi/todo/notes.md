# Задачи на будущее

## Provide additions settings for agents
Добавить в конфигурационной файл агентов опциональный параметр `additions` в котором будут записываться настройки для агентов, которые носят опциональный и уникальный характер для каждого из агентов.

## Remove AgentKind
Необходимо избавиться от AgentKind (см `crates\conf\src\types.rs`) и всей связанной логике, которая занимает переводом псевдонима имени модели в имя модели, оправляемое в запросе.

Ожидаемый эффект:
1. Во всех файлах конфигурации агентов ключ `name` уже содержит отправляемое имя модели;
2. Добавление новой модели известного вендора не требует перекомпиляции исходного кода.

## Very long thinking
В некоторых запросах, умные модели (Grok-4.6, DeppSeek-4-Pro, CloudSonnet-5.5) могут очень долго отвечать на очередной request в виду долгого цикла внутренних рассуждений (больше 2 минут), что по итогу приводит к тому, что ожидание ответа падает по timeout.

Пример:
```md
## Iteration №15
Usage:
- time = 3 min 24 sec
- tokens = 63918
- USD approximated = 0.31
- USD real = 0.38
⚠️ 1-attempt request failed: error sending request for url (https://api.x.ai/v1/chat/completions)
⚠️ 2-attempt request failed: error sending request for url (https://api.x.ai/v1/chat/completions)
⚠️ 3-attempt request failed: error sending request for url (https://api.x.ai/v1/chat/completions)
⚠️ 4-attempt request failed: error sending request for url (https://api.x.ai/v1/chat/completions)
```

Подобное поведение приводит к тому, что harness разрывает соединение так и не дождавшись ответа, повторяет попытку, которая вновь выполняется очень долго, что по итогу приводит к зацикливанию запросов и бессмысленному потреблению токенов.

Такое поведение необходимо исправить:
- ответ за запрос может ожидаться бесконечно долго
- только пользователь может завершить ожидание ответа явным прерыванием процесса агентского цикла
- процесс ожидания должен быть асинхронным и наблюдаемым для пользователя → пусть в консоли во время ожидания ответа постоянно обновляется секундомер: `response waiting time: 1 min 40 sec`
  - в логах этот секундомер фигурировать не должен
  - секундомер должен обновлять значение в консоли каждую секунду
  - чтобы консольный вывод не засорялся, необходимо перезаписывать последнюю строку


## Client/Server implementation
Необходимо реализовать возможность клиент-серверного взаимодействия, где серверная часть это harness.exe запущенный в режиме сервера, а клиент - это harness.wasm - pure Rust reactive web-assembly приложение на Leptos.

### Server site
Требования к запуску:
* Добавить CLI параметр `--serve`, использование которого запускает harness.exe в режиме сервера.
* Добавить CLI параметр `--port`, используемый вместе с `--serve`, определяющий порт, на котором будет доступен сервер.

Пример: `harness.exe --serve --port 4067` → доступен по адресу `http://localhost:4067`.

### Client Site
`harness.wasm` представляет из себя простое web-приложение которое является клиентом для `harness.exe`, запущенного локально или где-то на удалённом сервере, которое позволяет запускать агентские циклы, выполняющиеся на машине сервера, но с отслеживанием прогрессов и статусов на машине клиента через web-интерфейс.

Ключевые ожидаемые возможности:
- формирование промпта и запуск агентского цикла;
- выбор агента для цикла из списка доступных;
- отслеживание прогресса путём вывода логов процесса работы агентского цикла;
- остановка запущенной сессии;
- очистка окна логов;

Заметка: данная задача требует детальной проработки цикла клиент серверного взаимодействия, согласования REST-API, и интерфейса пользователя, что, вероятно, потребует множества итераций планирования и согласования, однако, для первой итерации необходимо проявить фантазию и составить полноценный рабочий план на реализацию (если, что-то будет не так, не страшно, будет дорабатывать), опираясь на те не многие базовые требования, которые здесь сформулированы.
