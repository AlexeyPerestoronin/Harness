# Задача на разработку: RPM / TPM / RPD для всех моделей и общий слой запросов
Сделать `rpm`, `tpm`, `rpd` обязательными полями **каждого** файла агента (`-1` = параметр не учитывается) и вынести ожидание лимитов + цикл повторов в модуль `crates/harness/src/vendor_request.rs`. Сейчас RPM реально применяется только в `GoogleAgent`; у xAI стоит заглушка `sleep(15s)`; у Claude ретраев нет; `tpm`/`rpd` нигде не используются.

Зачем: одна согласованная политика «сколько можно стучать в API» для всех вендоров, включая тех, кто появится в задаче 6.

Предусловие: не зависит от dump/skills. Файлы агентов (`agents/*.json5`) трогаем только в части rpm/tpm/rpd.

Ожидаемый результат: Grok и Claude имеют в json5 `"rpm": -1, "tpm": -1, "rpd": -1`; Gemini сохраняет свои числа; все три агента ходят в сеть через общий слой, который перед запросом ждёт RPM/TPM/RPD, а при 429/503/transport error повторяет попытку (до 24 раз).

## Функциональные требования
### 1. Конфигурация модели
1. `rpm`, `tpm`, `rpd` обязательны для **любого** вендора. Тип в json5 — число. В `AgentSettings` сменить `Option<u32>` на `i64` (как `token_limit`).
2. Допустимые значения: `-1` (лимит выключен) или целое `>= 1`. `0`, дробные, отсутствие ключа — ошибка:
   - нет ключа: `please define 'rpm' in the model conf file` (то же для tpm/rpd);
   - не число / не целое / `0` / `< -1`: `'rpm' must be -1 or a positive integer`.
3. Убрать спецветку «Google требует rpm». Google-файлы уже содержат положительный rpm — они остаются валидными.
4. Обновить все существующие файлы агентов (и копии в `WiKi/harness/agents/`, если там те же модели):
   | Файл | rpm | tpm | rpd |
   |---|---|---|---|
   | `agents/grok-4.6.json5` | `-1` | `-1` | `-1` |
   | `agents/claude-sonnet-5-5.json5` | `-1` | `-1` | `-1` |
   | `agents/gemini-3.8-flash.json5` | как сейчас (`5` / `250000` / `20`) | | |
   | `agents/gemini-3.5-flash-lite.json5` | как сейчас (`15` / `250000` / `500`) | | |
   | `agents/gemini-3.1-flash-lite.json5` | как сейчас (`15` / `250000` / `500`) | | |
   Поля `token-limit` / `iteration-limit` / `USD-limit` / `api-key` не менять.
5. `GoogleAgent::new` больше не делает `agent.rpm.ok_or_else`. Все агенты получают три `i64` и передают их в слой запросов.

### 2. Модуль `vendor_request.rs`
1. Создать `crates/harness/src/vendor_request.rs`, подключить в `mod.rs` / `main.rs` crate `harness`.
2. Исходная формулировка предлагала `reqwest-middleware`. Harness использует **blocking** `reqwest` и **не имеет** tokio. `reqwest-middleware` / `reqwest-retry` — async. **Не** вводить async runtime.
   - Реализовать свой blocking pipeline, в котором проверки разделены по типам (rate-limit и retry — разные функции/типы, не портянка в `execute_request` каждого агента).
   - Если найдётся blocking-crate, который делает это лучше без tokio — можно взять, но в `result.md` обосновать, чем он лучше 30–80 строк своего кода. Иначе — свой модуль, новых зависимостей нет.
3. Клиент: агент по-прежнему владеет `reqwest::blocking::Client` (timeout 300s, как сейчас) либо получает его из модуля — на усмотрение, без дублирования builder-логики в трёх файлах, если это дёшево.
4. Публичный минимум (имена свободны):
   - конструктор из `(rpm, tpm, rpd)` и `Arc<dyn Logger>`;
   - метод «перед запросом подожди лимиты»;
   - метод «отправь request, повтори по политике, верни `Response` или ошибку».
   Агенты **не** содержат собственных циклов `for attempt in 1..=24` и `wait_rate_limit` после этой задачи.

### 3. Семантика лимитов
`-1` в любом из трёх параметров → эта проверка пропускается.

**RPM** (как сейчас у Google, без магических 15 секунд xAI):
- минимальный интервал между **началами** запросов = `60 / rpm` секунд;
- если прошло меньше — sleep на недостающее `+ 1.0` секунду (как `GoogleAgent::wait_rate_limit`);
- `rpm == -1` → не ждать.

**TPM** (токены в скользящие 60 секунд):
- после **успешного** ответа учесть `input_tokens + output_tokens` (если агент знает cached — можно не вычитать: TPM это нагрузка на API, не биллинг);
- перед следующим запросом, если сумма в окне `>= tpm`, спать до выхода самой старой записи из окна;
- токены текущего ещё не отправленного запроса не оценивать заранее;
- один ответ больше `tpm` не фейлит запрос: следующее ожидание будет до 60с.

**RPD** (запросы в скользящие 24 часа, UTC-instant, без таймзоны вендора):
- считать только попытки, которые дошли до HTTP (включая 429/503);
- если `count >= rpd`, спать до выхода самой старой записи из окна.

Состояние окон — в слое запросов, на экземпляр агента (не глобально на процесс). В dump **не** сериализовать (после `--dump` лимиты стартуют с нуля — это ок, зафиксировать в `result.md`).

### 4. Цикл повторов
Единый для всех вендоров, max **24** попытки (как Google):
| Ситуация | Действие |
|---|---|
| HTTP 429 | лог в стиле `fail 429: model limit exceeded!`, затем wait по RPM/TPM/RPD, retry |
| HTTP 503 | лог `fail 503: waiting {n}s...`, sleep случайных `5..=20` секунд (`rand`, уже в зависимостях), retry |
| Ошибка транспорта (`send`/`read body` failed) | лог с номером попытки (как xAI `⚠️ {attempt}-attempt ...`), wait по лимитам, retry |
| Другой HTTP (4xx/5xx кроме 429/503) | сразу `Err("... HTTP {status}: {body}")`, без retry |
| 24 неудачи | `Err` с последней причиной |

Успешный HTTP 2xx выходит из цикла, агент парсит body как сейчас.

### 5. Правки агентов
1. `google.rs`: удалить `wait_rate_limit`, цикл 24, обработку 429/503. Поле `rpm: u32` убрать. Вызов слоя — в `execute_request`. Парсинг ответа, history, pending, dump — не трогать.
2. `xai.rs`: удалить `wait_rate_limit` с `sleep(15s)` и свой цикл 24. `execute_request` собирает URL/заголовки/body как сейчас (`Authorization`, `x-grok-conv-id`) и отдаёт отправку слою.
3. `claude.rs`: обернуть единственный `client.post` в тот же слой (появятся ретраи, которых не было).
4. Не менять учёт токенов/USD, URL, заголовки, парсеры.

## Проверка корректности решения
1. `cargo test --workspace`. Живые API не вызывать.
2. Тесты `conf`: grok-файл с тройкой `-1` грузится; отсутствие `rpm` — ошибка; `rpm: 0` — ошибка; Gemini с положительными числами — как раньше.
3. Тесты `vendor_request` без сети (подмена часов/sleep через параметр или маленький trait, **не** реальный sleep на 60с):
   - все три `-1` → wait возвращается сразу;
   - rpm=2: два вызова подряд требуют ожидания порядка `30+1` секунд (проверить запрошенный delay, не `thread::sleep`);
   - tpm=100: после учёта 100 токенов следующий wait > 0;
   - rpd=1: второй «засчитанный» запрос ждёт;
   - политика retry: 429 → retry, 400 → нет retry (мок транспорта).
4. Существующие unit-тесты парсеров Google/xAI/Claude зелёные.
5. Ручной шаг не обязателен. 15-секундный sleep xAI должен исчезнуть (grep `from_secs_f64(15`).
