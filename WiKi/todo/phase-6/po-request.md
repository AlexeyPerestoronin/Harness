# Client/Server implementation
Необходимо реализовать возможность клиент-серверного взаимодействия, где серверная часть это `harness.exe` запущенный в режиме сервера, а клиент - это `harness.wasm` - pure Rust reactive web-assembly приложение на Leptos.

## Server site
Требования к запуску:
* Добавить CLI параметр `--serve`, использование которого запускает `harness.exe` в режиме сервера.
* Добавить CLI параметр `--port`, используемый вместе с `--serve`, определяющий порт, на котором будет доступен сервер.

Пример: `harness.exe --serve --port 4067` → доступен по адресу `http://localhost:4067`.

## Client Site
`harness.wasm` представляет из себя простое web-приложение которое является клиентом для `harness.exe`, запущенного локально или где-то на удалённом сервере, которое позволяет запускать агентские циклы, выполняющиеся на машине сервера, но с отслеживанием прогрессов и статусов на машине клиента через web-интерфейс.

Ключевые ожидаемые возможности:
- формирование промпта и запуск агентского цикла;
- выбор агента для цикла из списка доступных;
- отслеживание прогресса путём вывода логов процесса работы агентского цикла;
- возможность остановки/прерывания запущенной сессии;
- возможность удалённой коммуникации с пользователем (задавать вопросы, запрашивать разрешения и т.д. → всё, что есть в `user`-tool)

Важные моменты:
- важна возможность использования в качестве полноценного самодостаточного web-приложения
- важна возможность интеграции в другие Leptos web-assembly pure-Rust приложения в качестве подключаемого модуля через WAI (Web Assembly Interface) (подобно тому, как подключаются плагины в VSCode, которые расширяют возможности IDE своими возможностями через API)
- UI web-интерфейс должен быть простым и адаптивным, чтобы быть способным помещаться в небольшие выделенные пространства при подключении в виде модуля

# Что необходимо сделать:
1. Данная задача требует детальной проработки цикла клиент серверного взаимодействия, согласования REST-API, WAI-API и интерфейса пользователя;
2. В виду сложности задачи планирование будет происходить в несколько итераций прежде чем оформится итоговое видение того, как это должно выглядеть и работать.
   1. Данная итерация планирования является первой по результатам которой необходимо предложить подробное и детальное описание того, как именно может быть реализована описанная задача (не нужно формировать задачи, только анализ и формирование предложений по реализации).
3. Допускается гибкость в использовании технологий с критикой предложенных и выдвижением альтернатив.

# Решения Project Owner (упрощение реализации)

По итогам ревью пакета консультационных документов Project Owner зафиксировал следующие решения, обязательные для пятой итерации планирования:

1. **TLS-артефакты.** Самоподписанные сертификаты и приватный ключ хранить в каталоге данных ОС (`%LOCALAPPDATA%` на Windows), вне `cwd`, чтобы они не были доступны через файловое API.

2. **Выбор агента и API-ключ.** Убрать из web-клиента всю логику выбора агентов и ввода API-ключа.
   - Если на стороне сервера в `harness.json5` не определена конкретная конфигурация агента, сервер запрашивает выбор через модуль `Interaction`.
   - Ввод API-ключа также запрашивается сервером через `Interaction`.
   - Для web-клиента такие запросы выглядят как обычный запрос на взаимодействие с пользователем: никакой отдельной логики и никакого отдельного API для агентов/ключей на клиенте нет.

3. **Лог сессии и транспорт.** Отменить показ лога сессии в web-клиенте.
   - Убрать SSE.
   - Убрать всё API, связанное с логом.
   - Web-клиент не должен ничего знать о том, что на стороне сервера пишется какой-то лог.
   - При запуске агентской сессии сервер возвращает клиенту URL-hook, по которому клиент проверяет статус сессии, наличие запросов на взаимодействие и результат по завершении.
   - Web-клиент раз в 10 секунд опрашивает URL-hook и на основании статуса выполняет действия: ожидает завершения, показывает запрос на взаимодействие, показывает результат.
   - Всё работает только по HTTPS через Axum; никаких других протоколов не использовать.
