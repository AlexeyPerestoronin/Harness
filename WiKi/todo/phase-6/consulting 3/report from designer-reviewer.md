> Объект ревью: пакет документов Project Consultant `WiKi/todo/phase-6/consulting 3/`:
> `base.md`, `arch.md`, `tech.md`, `api.md`, `ui.md`.
>
> Статус: **отправить на доработку** с обязательным устранением критических замечаний.
> Общая оценка: концепт жизнеспособен и в целом соответствует решениям Project Owner, но в текущем виде содержит несколько сквозных противоречий и один критический пробел в безопасности.

---

## 1. Резюме

Пакет №3 — это финальное консолидированное видение клиент-серверной реализации Phase 6. Консультант корректно учёл предыдущие решения Project Owner: одна активная сессия без `SessionManager`, декомпозиция на `cli-harness`/`web-harness`/`agent-loop`, единый интерфейс `Interaction`, упрощённый `Logger`, RSA-передача API-ключа, отсутствие статики на сервере, `live-timeout`, Source-Level интеграция через Cargo/Git, отсутствие удалённого запуска/скачивания `harness.exe`.

Сильные стороны — последовательная асинхронная архитектура, удачное разрешение вопроса о направлении зависимостей `logger`/`interaction`, честные trade-off таблицы и разумное следование KISS/YAGNI.

Однако пакет нельзя принимать как есть. Главная причина — **заявленный принцип «секреты не покидают сервер» не обеспечен механизмами**: FS API и `GET /config` отдают сырое содержимое файлов, а в `cwd` физически лежат файлы агентов с полем `api-key`. В сочетании с CORS `*` и отсутствием аутентификации это даёт практический вектор кражи ключей из браузера пользователя. Кроме того, между документами есть несостыковки: в UI не описан ввод API-ключа, заявленный механизм SSE `Last-Event-ID` не реализован в приведённом коде, а структура `web-harness` не содержит бинарной точки входа для Trunk.

## 2. Что хорошо

1. **Точное следование решениям Project Owner.**
   - Одна активная сессия, без `SessionManager` (`arch.md` §7, `base.md` §3.1).
   - Сервер — чистый REST+SSE, не раздаёт статику и ничего не знает о клиенте (`base.md` §3.1).
   - `harness.exe` без параметров запускается в режиме сервера на порту по умолчанию (`base.md` §3.1, `arch.md` §7.1).
   - Source-Level интеграция `web-harness` через Cargo/Git, runtime-загрузка `.wasm` и WIT отложены (`base.md` §3.3, `arch.md` §10).
   - Сценарии удалённого запуска/скачивания убраны; вместо них — модальное окно с инструкцией (`ui.md` §3.2).

2. **Корректное разрешение спорного места о зависимостях.**
   В `arch.md` §2.3 явно объяснено, почему `interaction → logger`, а не наоборот: `interaction` хранит `dyn Logger`, и обратная зависимость создала бы цикл. Это правильная инженерная трактовка требования «logger → interaction → остальные крейты»: `tools`, `agent-loop`, `cli-harness` зависят от `interaction` и не зависят от `logger` напрямую.

3. **Удачная модель `Logger` + `Interaction` + `InteractionLoggers`.**
   - `Logger::log_str(message, new_line)` точно соответствует требованию PO.
   - `Interaction::input(prompt, write_log)` исправляет очевидную опечатку в эскизе PO (`fn input(&self, write_log: bool)` без prompt и без результата) и возвращает `Result<String, InteractionError>` — это обоснованное улучшение.
   - Группировка `file`/`progress` корректно выражает правило «при `write_log=false` файл не пишется, но клиенту событие уходит» (`arch.md` §5.3). Решение лучше, чем плоский `Vec<dyn Logger>`.

4. **Продуманная асинхронная модель.**
   - `VendorRequest` переводится на async с сохранением retry/rate-limit логики; блокирующие инструменты (`fs`, `git`, `terminal`) выносятся в `spawn_blocking` (`arch.md` §6.1, `tech.md` §3.1).
   - Отмена через `CancellationToken` + `tokio::select!` описана для HTTP-запроса и для ожидающего `input` (`arch.md` §6.2).
   - Честно зафиксировано ограничение: полная гарантия отмены зависит от поведения вендорного API (`base.md` §5.3).

5. **Жизнеспособный UX первого запуска.**
   - Сервер стартует при отсутствии/невалидной конфигурации с состояниями `configState: ok|missing|invalid` (`arch.md` §7.4).
   - `GET /config` при отсутствии файла возвращает шаблон, `POST /config/default` идемпотентно создаёт конфигурацию (`api.md` §4).

6. **Соблюдение KISS/YAGNI.**
   - Без аутентификации, без TLS в самом сервере, без WebSocket, без runtime-плагинов, без `SessionManager`, plain CSS без Tailwind (`base.md` §5, `tech.md` §4.1, `ui.md` §5.3).
   - SSE выбран осознанно и обоснованно: команды клиента идут через REST, двунаправленный канал не нужен (`tech.md` §4.1).

7. **Документы самодостаточны.**
   Требование PO «не ссылаться на предыдущие итерации» выполнено: пакет №3 читается как самостоятельный документ.

## 3. Что плохо

### 3.1. Критические замечания (блокеры)

#### Б1. «Секреты не возвращаются клиенту» не обеспечено: FS API и `GET /config` отдают сырые файлы с `api-key`

- `api.md` §1 декларирует: *«Секреты (`api-key`, приватный RSA-ключ) никогда не возвращаются клиенту»*.
- При этом `api.md` §8 (`GET /api/v1/fs/read`) возвращает сырой текст любого файла внутри `cwd`, а `api.md` §4 (`GET /api/v1/config`) возвращает сырой текст `harness.json5`.
- В текущем репозитории файлы `harness/agents/*.json5` содержат поле `api-key` (сейчас в них заглушки, но в реальной эксплуатации — ключи), и эти файлы находятся внутри `cwd`.
- Ни в одном документе пакета не описан механизм редкации секретов для `GET /config` и FS-чтения.

**Почему это плохо.** Это не гипотетическая, а прямая утечка: `GET /api/v1/fs/read?path=harness/agents/deepseek-v3.json5` вернёт ключ. С учётом CORS `*` и отсутствия аутентификации (см. Б2) ключ может прочитать любая веб-страница, открытая у пользователя.

**Как исправить.**
- Ввести серверную редкацию полей `api-key` (и аналогичных секретов) во всех ответах FS API и `GET /config`; на UI возвращать `api-key: "***"` или `"<redacted>"`.
- Для `PUT /config` и `PUT /fs/write` определить merge-правило: если клиент прислал редкатированное значение — сохранить старое значение секрета, а не затирать его.
- Как минимум — запретить чтение/запись `harness/agents/*` через общий FS API и вынести работу с ключами только в RSA-эндпоинты.
- Обязательно покрыть это тестами: `GET /fs/read` файла агента не должен содержать `api-key`.

#### Б2. CORS `*` + отсутствие аутентификации + FS-write/run API = CSRF-подобный вектор атаки на локальный сервер

- `tech.md` §7.1 задаёт `server.cors-origin` по умолчанию `"*"`.
- `base.md` §5.5 фиксирует: *«Аутентификация в первой версии не вводится; по умолчанию сервер слушает 127.0.0.1»*.
- `api.md` §8 даёт REST-запись/удаление/перемещение файлов, а `POST /api/v1/run` запускает цикл.

**Почему это плохо.** `127.0.0.1` защищает от внешнего сетевого доступа, но **не защищает от браузера пользователя**. При CORS `*` любой сайт, открытый в браузере, может выполнить `fetch("http://localhost:4067/...")`: прочитать логи/конфигурацию/файлы агентов (см. Б1), записать файлы ролей/навыков в `cwd`, запустить агентский цикл или удалить файлы. Запись в `roles/`/`skills/` — это прямой путь к prompt injection; далее агент может запросить подтверждение команды, и пользователь рискует одобрить вредоносное действие. Это фактически локальный RCE-вектор.

**Как исправить.**
- По умолчанию CORS должен быть **выключен или ограничен явным allowlist** (origin GitHub Pages и `http://localhost:<trunk-port>`), а `*` — только как осознанная пользовательская настройка с предупреждением.
- Для `--host 0.0.0.0` дополнительно требовать подтверждения/предупреждения; как минимум не разрешать `0.0.0.0` вместе с `cors-origin: "*"` без явного флага.
- Рассмотреть дешёвую защиту от сторонних origin: проверка заголовков `Origin`/`Sec-Fetch-Site` и отказ для cross-site запросов к мутирующим эндпоинтам.
- Даже если PO решил «токен не обязателен», это не отменяет необходимости закрыть cross-site-доступ; токен и CORS — разные слои защиты.

#### Б3. В UI не описан ввод API-ключа, хотя RSA-флоу обязателен

- `arch.md` §9 и `api.md` §5 описывают флоу: `GET /crypto/public-key` → шифрование → `POST /crypto/api-key`.
- `tech.md` §5.2 и `ui.md` §2 перечисляют компоненты: `ConnectDialog`, `StatusBar`, `AgentSelector`, `PromptComposer`, `LogView`, `InputModal`, `ConfigEditor`, `FsBrowser`, `ConnectDialog` — **компонента ввода API-ключа нет**.
- В пользовательских сценариях (`ui.md` §4) шаг «ввести API-ключ» отсутствует.

**Почему это плохо.** Клиент не сможет выполнить обязательный сценарий для агентов с `apiKeyRequired: true`. На уровне UI образуется разрыв между API и интерфейсом.

**Как исправить.** Добавить в `ui.md` компонент `ApiKeyModal`/`ApiKeyField` и сценарий: при выборе агента с `apiKeyRequired` открывать ввод ключа, выполнять RSA-флоу, показывать состояние «ключ принят», обрабатывать ошибки расшифрования/таймауты. Дополнить структуру `web-harness` в `tech.md` §5.2 файлом `components/api_key_modal.rs`.

#### Б4. Заявленный механизм SSE `Last-Event-ID`/replay не реализован в приведённом дизайне

- `tech.md` §4.4 обещает: *«События получают монотонный id. Клиент использует Last-Event-ID. Сервер держит кольцевой буфер последних 512 событий»*.
- Приведённый SSE-хендлер (`tech.md` §4.3) просто подписывается на `tokio::sync::broadcast` и отдаёт события по мере поступления. Он не читает заголовок `Last-Event-ID`, не имеет доступа к кольцевому буферу и не выставляет `Event::id(...)`.
- `tokio::sync::broadcast` принципиально не умеет replay по ID: при подписке можно получить только новые события; при `Lagged` клиент отпадает.

**Почему это плохо.** Обещание «переподключение с Last-Event-ID» не соответствует механизму. Клиент, построенный по `ui.md` §7 и `tech.md` §4.4, будет рассчитывать на replay, которого нет.

**Как исправить.** Выбрать один из вариантов:
- реализовать поверх broadcast явный кольцевой буфер `VecDeque<(u64, ServerEvent)>` и при подключении читать `Last-Event-ID`, отдавать накопленные события, затем live-подписку; в SSE-хендлере выставлять `.id(id)`;
- либо честно убрать `Last-Event-ID` из контракта и оставить восстановление только через `GET /run` + `GET /run/log`, явно указав это в `tech.md` §4.4 и `ui.md` §7.
В обоих случаях в примере кода должен фигурировать `Event::default().id(...)`.

#### Б5. Для standalone-сборки `web-harness` не хватает бинарной точки входа

- `tech.md` §5.2 описывает структуру `crates/web-harness` только с `src/lib.rs` и `index.html`.
- Trunk для Leptos CSR ожидает бинарный таргет (`src/main.rs`), который монтирует приложение; библиотечный крейт без bin-таргета не соберётся в standalone WASM без дополнительных ухищрений.

**Почему это плохо.** Заявленный артефакт `harness.wasm`/`dist` для GitHub Pages может не собраться стандартной командой `trunk build --release`, а интеграция в родительское приложение требует библиотеки. Нужно явно зафиксировать dual-layout.

**Как исправить.** В `tech.md` §5.2 и `arch.md` §2.1 указать: `lib.rs` экспортирует `HarnessGateway`, `HarnessClient`, `HarnessPanel`; тонкий `main.rs` монтирует `HarnessApp` в `window` для standalone. Либо описать настройку Trunk под lib-таргет, если выбран такой путь.

#### Б6. Несогласованность таймаута ожидания ввода

- `arch.md` §5.2 объявляет `InteractionError::Timeout`, а `arch.md` §8.2 упоминает «ожидание oneshot с таймаутом».
- Но нигде в пакете №3 нет параметра конфигурации для этого таймаута (в `server` его нет), и в state-диаграмме `arch.md` §7.3 нет перехода `WaitingInput → Failed/Timeout`.

**Почему это плохо.** Реализатор не знает, какой таймаут закладывать и что делать при его истечении; контракт `InteractionError` расходится с моделью состояний.

**Как исправить.** Либо добавить `server.input-timeout` (минуты, значение по умолчанию) и переход `WaitingInput → Failed`/`Stopped` по таймауту, либо убрать `Timeout` из первой версии и оставить только `Cancelled`/`Io`.

### 3.2. Существенные замечания

#### С1. Отмена не покрывает чтение тела ответа вендора

В `tech.md` §3.2 `tokio::select!` обёрнут только `client.post(...).send()`, а `resp.text().await` выполняется уже внутри выбранной ветки и не отменяется по `cancel`. Для «думающих»/streaming-моделей значительное время занимает именно чтение тела ответа, поэтому кнопка Stop может не сработать мгновенно, как обещано в `base.md` §5.3.

**Исправление.** Заворачивать в `tokio::select!` всю операцию `send + read body` (например, отдельная `async fn`/`async` блок) либо проверять `cancel` между чтениями чанков.

#### С2. Типы блокировок в `ServerState` не уточнены

`arch.md` §7.2 использует `RwLock` и `Mutex` без указания `std::sync`/`tokio::sync`. В async-обработчиках axum использование `std::sync::RwLock` допустимо только при гарантии, что guard не удерживается через `.await`; в противном случае возможна блокировка runtime.

**Исправление.** Явно зафиксировать `tokio::sync::RwLock`/`tokio::sync::Mutex` для полей `config`/`active`/`encrypted_keys` либо написать инвариант «lock не удерживается через await».

#### С3. `GET /run/events` в состоянии `idle` не определён

`api.md` §7 не описывает поведение SSE при отсутствии активного цикла: держать соединение, сразу закрывать, слать `status: idle`? `ui.md` §7 упоминает reconnect, но серверная часть контракта недоопределена.

**Исправление.** Зафиксировать: SSE при `idle` возвращает `status` с `runState: idle` и остаётся открытым (или закрывается) — и описать соответствующее поведение клиента.

#### С4. Риск смешанного контента для GitHub Pages → `http://localhost`

Standalone-клиент размещается на HTTPS (GitHub Pages), а сервер — HTTP. Современные браузеры в целом разрешают `http://localhost` из secure context, но поведение для `http://127.0.0.1` и удалённых HTTP-хостов менее однородно. Пакет не упоминает этот нюанс.

**Исправление.** В `ui.md` §3.1/`tech.md` §7 зафиксировать: использовать `http://localhost:<port>`, а для удалённого доступа — HTTPS через обратный прокси; добавить явную диагностику ошибок mixed-content/CORS в UI.

#### С5. `live-timeout` может оборвать пользователя во время редактирования конфигурации/файлов

Таймер продлевается только активным циклом. Если пользователь 5+ минут редактирует `harness.json5` или файлы ролей/навыков и не запускает цикл, сервер завершится. Формально это соответствует решению PO, но UX-сценарий редактирования это не учитывает.

**Исправление.** Обсудить с PO два варианта: (а) оставить как есть, но явно указать в UI «сервер завершится через N минут простоя»; (б) приостанавливать таймер, пока открыто SSE-соединение клиента, или сбрасывать его при `PUT /config` и мутирующих FS-операциях.

#### С6. FS API позволяет удалить/перезаписать `harness.json5`, логи и служебные файлы

`DELETE /fs/remove` и `PUT /fs/write` работают по всему `cwd`. Удаление `harness.json5` или активного лога не запрещено и не предупреждается.

**Исправление.** В UI добавить подтверждение деструктивных операций; на сервере — защитить `harness.json5` от удаления во время активного цикла; как минимум документировать поведение.

#### С7. RSA-OAEP-256 на ключе 2048 бит не описан для длинных ключей

RSA-OAEP(SHA-256) с 2048-битным ключом позволяет зашифровать не более 190 байт. Для типичных API-ключей этого достаточно, но контракт не задаёт максимальную длину `encryptedApiKey`/открытого ключа.

**Исправление.** Зафиксировать ограничение длины API-ключа (например, 128–190 байт) и возвращать `400` при превышении; либо поднять ключ до 3072 бит; либо предусмотреть гибридную схему (RSA-OAEP + AES-GCM), если допускаются длинные ключи.

## 5. Что можно улучшить

1. **Унифицировать терминологию crate'а `interaction`/`interactions`.** В пакете №3 используется `interaction` (единственное число). Это соответствует последнему указанию PO, но если в кодовой базе/задачах встречается `interactions`, нужно явно зафиксировать каноническое имя.

2. **Добавить в `ui.md` сценарий «ввести API-ключ»** (связано с Б3) и отразить его в `ui.md` §4 и §6.

3. **Явно описать восстановление UI после reconnect.** `ui.md` §7 и `api.md` §6 упоминают `pendingInput`, но стоит свести это в одну таблицу «состояние → какие запросы делает клиент после восстановления SSE» (`GET /run`, `GET /run/log`, повторное открытие `input_request`).

4. **Зафиксировать поведение `GET /run/events` при `idle`** (связано с С3).

5. **Уточнить реакцию на повторный `POST /run/stop`** (идемпотентность: `202`/`409`/`200`) и на `POST /run/input` после отмены.

6. **Добавить query-параметр `?server=` для standalone-клиента.** Это упростит сценарий «открыл с GitHub Pages и сразу подключился», не меняя архитектуру.

7. **Отразить в `web-harness` мост EventSource → `Stream`.** `HarnessGateway::events() -> impl Stream<Item = ServerEvent>` нетривиален поверх callback-based `EventSource`; стоит либо явно описать использование `futures::stream::unfold`/канала, либо заменить на callback-подписку (`on_event(...)`) в первой версии.

8. **Синхронизировать `Logger` и `Interaction` в части прогресса.** В `arch.md` §8.2 показано логирование prompt только в `FileLogger`; по таблице §5.3 прогресс-приёмники тоже должны получать события. Стоит явно указать, что prompt вопроса дублируется и в SSE-лог, чтобы вопрос был виден не только в модальном окне.

9. **Добавить юнит-тесты контрактов.** Для `harness-api` — сериализация/десериализация DTO и событий; для FS API — нормализация путей, отклонение `..`, absolute path, symlink-выходов; для RSA — ограничение длины и round-trip.

## 6. Итоговый вердикт

**Отправить на доработку Project Consultant.**

Концептуальное направление утверждается: стек axum + tokio + async reqwest, REST + SSE, Leptos CSR + Trunk, Source-Level интеграция, одна активная сессия, RSA-передача ключа — всё это согласовано и реализуемо в рамках текущей кодовой базы.

Но перед началом декомпозиции на задачи необходимо закрыть шесть блокеров:

1. **Б1** — редкация/защита секретов в `GET /config` и FS API.
2. **Б2** — безопасная политика CORS по умолчанию и защита от cross-site-запросов.
3. **Б3** — UI-компонент и сценарий ввода API-ключа.
4. **Б4** — непротиворечивый механизм SSE replay (`Last-Event-ID` + кольцевой буфер) или его осознанное исключение.
5. **Б5** — бинарная точка входа для standalone-сборки `web-harness`.
6. **Б6** — определённое поведение таймаута ожидания ввода.

После устранения блокеров и внесения существенных правок (С1–С7) план можно принимать в работу. Альтернативный архитектурный путь не требуется: выбранная архитектура адекватна задаче, менять нужно не каркас, а конкретные контракты безопасности и согласованность документов.
