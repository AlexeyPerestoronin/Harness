# Задача на исправление: request time-counter не отсчитывает секунды ожидания ответа

## Как есть сейчас:
В консольном лог-output агентской сессии при ожидании ответа вендора выводится строка `response waiting time: X min Y sec`, но счётчик практически всегда показывает `0 min 0 sec` (иногда `0 min 1 sec`), хотя фактическое ожидание занимает секунды. Пример из тестирования PO:

```txt
## Iteration №4
Usage:
- time = 0 min 9 sec
- tokens = 5454
- USD approximated = 0.004468
response waiting time: 0 min 0 sec response
```

Причина: после миграции на async стек индикатор ожидания (`WaitingAction`) выполняется только во время `RequestBuilder::send()` — то есть до получения HTTP-заголовков ответа. Чтение тела ответа `response.text()` выполняется в `VendorRequest::send_json` уже после `RequestPipeline::execute`, без циклического индикатора. Для не-streaming моделей основное время занимает именно чтение тела, поэтому счётчик остаётся на `0 min 0 sec`.

## Как должно быть:
Строка `response waiting time: X min Y sec` должна обновляться в консоли каждую секунду на протяжении всего ожидания ответа вендора, включая чтение тела ответа, и показывать реально прошедшее время от начала попытки до полного получения тела. Служебная строка по-прежнему не пишется в файл `log.md` (`write_log = false`). Отмена через `CancellationToken` должна прерывать и ожидание заголовков, и чтение тела.

## Что необходим исправить:
В `crates/agent-loop/src/vendor_request.rs` в `VendorRequest::send_json`:

1. Сейчас чтение тела после `pipeline.execute` выполнено отдельным `tokio::select!` без DurAction-индикатора:
   ```rust
   let read_body = async { response.text().await.map_err(|e| transport_error(&e)) };
   let body = tokio::select! {
       _ = cancel.cancelled() => { return Err("request cancelled".into()); }
       result = read_body => result,
   };
   ```
2. Необходимо продолжать выполнение того же `WaitingAction` (или эквивалентного вывода) и во время чтения тела: раз в секунду выводить `response waiting time: {format_waiting_time(ctx.started_at.elapsed().as_secs())}` через `interaction.output(..., false, OutputType::RewriteLine)`.
3. Реализация должна оставаться минимально инвазивной: либо вынести «чтение тела с тикером» в отдельный helper, либо расширить `RequestPipeline` так, чтобы DurAction-действия продолжали выполняться до полного чтения тела. Главное — не дублировать retry/rate-limit логику.
4. retry-классификация (`429` / `503` / `transport` / `2xx` / `4xx`), `MAX_ATTEMPTS = 24`, формат `X min Y sec` и поведение отмены должны остаться без изменений.

## Проверка корректности исправления:
1. `cargo build --workspace` — успех, без warnings.
2. `cargo test -p agent-loop` — успех. Если реализация позволяет, добавить unit-тест на helper/индикатор, который проверяет, что при медленном чтении тела выводится минимум два значения с разными секундами; и что отмена токена прерывает чтение тела с ошибкой `request cancelled`.
3. Ручная проверка консольного запуска с реальным API-ключом: при ожидании ответа модели счётчик `response waiting time` увеличивается каждую секунду; при этом в файле `log.md` служебная строка отсутствует (`write_log = false`).
