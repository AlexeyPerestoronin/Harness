# Отчёт о состоянии кодовой базы — Phase 6 Refactoring

## 1. Контекст

Рефакторинг выполняется по факту завершения задач 6 фазы разработки. Цели рефакторинга зафиксированы Project Owner в `WiKi/todo/phase-6/po-detected-issues.md`:

1. Уменьшить количество кода там, где это возможно.
2. Уменьшить связность между отдельными компонентами там, где это возможно.
3. Актуализировать документацию:
   - оставить только английский язык;
   - добавить в `README.md` информацию об архитектуре приложения, используемых технологиях и базовых pipeline работы пользователя.

Дополнительно Project Owner описал три бага серверного/консольного режима и потребовал написать инструкцию по REST API. Последней задачей цикла рефакторинга должна быть очистка production-кода от всего, что не требуется на «боевом посту» (в первую очередь — unit-тестов).

## 2. Текущее состояние

Кодовая база после Phase 6 состоит из нативных крейтов:

- `logger` — контракт `Logger`, файловый/пустой приёмники;
- `interactions` — контракт `Interaction`, `CliInteraction`, `InteractionLoggers`;
- `auth` — Bearer-токен и axum-middleware;
- `harness-api` — общие DTO REST;
- `conf` — загрузка/валидация конфигурации, `ServerSettings`, `resolve_agent_for_run`;
- `tools` — реестр инструментов агента;
- `agent-loop` — асинхронный `AgentLoop`, вендорные агенты, `RequestPipeline`;
- `cli-harness` — консольный режим и HTTPS-сервер;
- `web-harness` — Leptos CSR-клиент (исключён из workspace, собирается Trunk).

`cargo build --workspace` и тесты выполняются успешно. При этом анализ выявил следующие проблемы.

## 3. Выявленные проблемы

### 3.1. Баги, описанные Project Owner

1. **Request time-counter.** В консольном логе `response waiting time` не отсчитывает секунды ожидания ответа, показывая `0 min 0 sec` или `0 min 1 sec`. Причина локализована в `crates/agent-loop/src/vendor_request.rs`: после миграции на async стек индикатор `WaitingAction` покрывает только ожидание HTTP-заголовков (`RequestBuilder::send()`), но не чтение тела ответа `response.text()`, которое у не-streaming моделей занимает основное время.

2. **`--serve` не печатает стартовую информацию.** `server::serve` выводит в stdout только Bearer-токен. Пользователь не видит параметры запуска: conf, cwd, host, порт, TLS, таймауты, CORS.

3. **Нет поиска свободного порта.** Если целевой порт занят, сервер завершается с ошибкой bind. Требуется последовательный поиск первого свободного порта с шагом `+1` и вывод статуса поиска.

### 3.2. Дублирование кода и связность

Консольный (`crates/cli-harness/src/main.rs`) и серверный (`crates/cli-harness/src/server/run.rs`) запуск сессии содержат дублирующиеся или почти дублирующиеся функции:

- `resolve_agent_for_run_interactive` — две реализации с разными типами ошибок;
- `prompt_api_key` — две реализации;
- `source_with_agent_config` — две реализации;
- `resolve_cwd_override` / `normalize_abs` — продублированы между `main.rs` и `server/mod.rs`.

Кроме того, `agent_loop::agent_select::choose` дублирует логику, которую серверный режим реализует через `build_prompt` + `parse_choice` вручную.

### 3.3. Документация

- В корне репозитория присутствует `README.ru.md`, а `README.md` ссылается на русскую версию. Это противоречит цели «только английский язык».
- В `README.md` отсутствуют явные разделы об архитектуре, используемых технологиях и базовых пользовательских pipeline.
- Отсутствует отдельная инструкция по REST API сервера (`REST-API.help.md`).

### 3.4. Код, не нужный в production

- `crates/logger/src/double.rs` (`DoubleLogger`) был оставлен только для компиляции старого бинарного крейта `harness`. Старый крейт удалён, поэтому `DoubleLogger` — мёртвый код.
- `crates/logger/src/null.rs` (`NullLogger`) не используется в production-коде workspace.
- По всем крейтам разнесены `#[cfg(test)]`-модули и тестовые dev-зависимости, которые не нужны в production-сборке.

## 4. Состав задач рефакторинга

| № | Задача | Тип | Основной scope |
|---|---|---|---|
| 1 | Исправить request time-counter | fix | `crates/agent-loop/src/vendor_request.rs` |
| 2 | Стартовая информация сервера и поиск свободного порта | fix | `crates/cli-harness/src/server/mod.rs` |
| 3 | Дедупликация кода запуска сессии | refactoring | `crates/cli-harness/src/**`, `crates/agent-loop/src/agent_select.rs` |
| 4 | Создать `REST-API.help.md` | docs | `REST-API.help.md` |
| 5 | English-only документация и README (архитектура, технологии, pipeline) | docs | `README.md`, `README.ru.md` |
| 6 | Очистка production-кода от тестов и мёртвого кода | refactoring | `crates/**` |

Порядок задач учитывает зависимости по файлам: задачи 1 и 2 закрывают баги PO; задача 3 затем устраняет дублирование в `cli-harness`; задачи 4 и 5 закрывают документационные цели; задача 6 выполняется последней и удаляет тесты/мёртвый код после того, как все изменения проверены.

## 5. Ожидаемый результат

После выполнения задач:

- `cargo build --workspace` и `trunk build --release` в `crates/web-harness` выполняются без ошибок и warnings;
- консольный и серверный режимы сохраняют внешнее поведение, за исключением явно исправленных багов и добавленной стартовой информации;
- в репозитории отсутствует русскоязычная пользовательская документация;
- `README.md` содержит архитектуру, технологии и базовые пользовательские pipeline;
- REST API задокументирован в отдельном файле `REST-API.help.md`;
- production-код очищен от unit-тестов, test-only зависимостей и мёртвого кода (`DoubleLogger`, `NullLogger` и т.п.).
