# Задача на исправление: стартовая информация сервера и поиск свободного порта

## Как есть сейчас:
`harness.exe --serve` (или без аргументов) в `crates/cli-harness/src/server/mod.rs` после загрузки конфигурации и генерации/парсинга Bearer-токена печатает в stdout только сам токен:

```rust
println!("{}", auth_token.as_base64url());
```

Никакой справочной информации о параметрах запуска не выводится.

Если целевой порт занят, `axum_server::bind_rustls(addr, rustls_config).serve(...).await` завершается с ошибкой bind. Поиск ближайшего свободного порта не выполняется.

## Как должно быть:
1. При запуске серверного режима в stdout выводится справочная информация о параметрах запуска:
   - режим и версия (`harness <version>`, server mode);
   - путь к `harness.json5`;
   - `cwd` (если определён);
   - `host` и целевой порт;
   - источник TLS (автогенерация в каталоге данных ОС или пользовательские `cert/key`);
   - `live-timeout` и `interaction-timeout`;
   - CORS allowlist (или `CORS disabled`, если список пуст);
   - Bearer-токен (как и раньше, чтобы клиент мог его скопировать);
   - итоговый URL `https://<host>:<port>`.
2. Если целевой порт занят, сервер последовательно проверяет порты с шагом `+1` до `65535` и выводит статус поиска, например:
   ```txt
   port 4067 is already in use, trying 4068...
   port 4068 is already in use, trying 4069...
   selected free port 4069
   ```
   После выбора свободного порта печатается фактический URL, и сервер поднимается на нём.
3. Если ни один порт до `65535` не свободен, сервер завершается с понятной ошибкой.
4. Печать Bearer-токена сохраняется в любом сценарии.

## Что необходим исправить:
В `crates/cli-harness/src/server/mod.rs`:

1. Выделить и дополнить вывод стартовой информации в `serve(...)` до запуска live-timeout задачи и до bind. Информацию формировать из уже вычисленных `ServeOptions`/`server`/`state` и `tls_paths`.
2. Заменить текущую логику `let addr = resolve_addr(&server.host, server.port).await?;` + `axum_server::bind_rustls(addr, ...)` на:
   - резолв `host` в `IpAddr`/`SocketAddr` один раз (текущий `resolve_addr` можно переиспользовать для начального порта);
   - цикл по портам от целевого до `65535`, в котором проверяется доступность порта (например, через `tokio::net::TcpListener::bind((ip, port)).await`, после чего listener сразу освобождается) и печатается статус;
   - запуск `axum_server::bind_rustls` на первом свободном порту.
3. Следить за тем, чтобы итоговый URL в стартовом блоке печатался после выбора фактического порта. Поэтому стартовый блок допустимо печатать в два этапа: параметры до поиска, а `listening on ...` после выбора порта.
4. Не менять поведение `GET /health` и прочих endpoint'ов; фактический порт должен использоваться только для bind.

## Проверка корректности исправления:
1. `cargo build --workspace` — успех, без warnings.
2. Ручная проверка №1: `cargo run -p cli-harness -- --serve --port 4067` — в stdout выводятся все перечисленные параметры и Bearer-токен, сервер поднимается на `https://127.0.0.1:4067`.
3. Ручная проверка №2: занять порт `4067` (например, вторым экземпляром или `python -m http.server 4067`) и запустить `cargo run -p cli-harness -- --serve --port 4067`. Убедиться, что выводятся шаги поиска, выбран свободный порт `4068` (или следующий свободный), и сервер доступен на этом порту.
4. Ручная проверка №3: `curl -k https://127.0.0.1:<фактический порт>/api/v1/health` возвращает `200` со `status: "ok"`.
