# Моменты которые необходимо доработать:
## Без сессий
Нет необходимости в возможности поддерживать множество сессий:
- одна активная сессия
- не нужен никакой SessionManager

## <web|cli>-harness
На уровне крейтов, необходимо реализовать следующую декомпозицию:
```
crates/
    web-harness/ # крейт ответственный за web-функционал (клиент)
    cli-harness/ # крейт ответственный за cli-функционал включая возможность запуска в режиме сервера (сервер)
    agent-loop/  # крейт ответственный за функционал агентского цикла (сейчас это крейт ./harness)
```

## Интерфейс Iteration
Не нужен никакой UserInteraction → достаточно одного интерфейса Interactions, который будет обязывать реализовывать два метода:
1. input - метод для ввода тестовой информации
2. output - метод для вывода тестовой информации

Данный интерфейс должен быть реализован для CLI и WEB версий (CLIIterations, WebInteraction).
Необходимо выделить в отдельный крейт: ./crates/interactions

## Передача API ключа
Запрос и передача API ключа должна быть доступна из Web-интерфейса и использовать для безопасности RSA-шифрование:
- при запросе на ввод API-ключа передаётся на сервере генерируется пара ключей и публичный ключ передаётся на клиент;
- клиент шифрует введённый API-ключ полученным публичным ключом и отправляет на сервер;
- сервер получив ключ, расшифровывает его и использует в сессии.

Данный функционал должен быть реализован в виде отдельного модуля в крейте web-harness.

## Взаимодействие сервера и клиента
1. Сервер ничего не знает о клиенте:
    - не содержит никакого web-интерфейса
    - если запущен, просто ожидает, что к нему подключится какой-нибудь клиент
      - если никто не подключился в течении 5 минут, самостоятельно отключается (`live-timeout` задаётся в файлах конфигурации сервера в `harness.json5`)
        ```json5
        {
            "cwd": "C:/MyLife/Harness",
            "server": {
                "port": 4343, // значение порта при запуске сервера, если за задан на прямую через CLI
                "live-timeout": 5, // время простоя с момента запуска или с момента окончания последнего цикла
                // возможно в дальнейшем здесь будут появляться ещё какие-то параметры;
            },
            "agent": {},
            "tools": {},
        }
        ```
    - на одной машине может запущено несколько серверов под уникальными портами

2. Клиент - это самостоятельное приложение в смысле жизненного цикла, но для полноценной работы которого необходим сервер:
    - 3 сценария взаимодействия с сервером:
        - Сценарий №1: клиент знает адрес и порт сервера и сервер запущен и ожидает подключение:
            - самый простой сценарий, когда клиент просто подключается к серверу по определённому порту
            - в этом случае, вероятно, не требуются никакие настройки, т.к. все необходимые метаданные для агентского цикла (модели, роли, умения) уже настроены и доступны
        - Сценарий №2: клиента знает адрес и CWD–папку сервера, но сервер не запущен:
            - в этом случае клиент должен запросить удалённую машину запустить процесс: `harness.exe --serve --port <port> --cwd <target working directory>`
            - если процесс успешно запущен, то подключиться к серверу
            - здесь, вероятно, тоже не потребуется никаких настроек метаданных для цикла
        - Сценарий №3: клиент знает только адрес машины на которой должен быть запущен сервер:
            - в этом случае, клиент запрашивает удалённую машину запустить процесс: `harness.exe --serve --port --cwd-new <temporary working directory>`
              - если процесс успешно запущен, то подключиться к серверу и произвести первичную метаданных агентского цикла
              - если процесс не запущен по причине отсутствия в системе исполняемого файла сервера → скачать с GitHub последнюю версию → запустить его в роли сервера → подключиться → произвести первичную настройку метаданных агентского цикла

Под метаданными агентского цикла подразумевается следующее:
1. CWD - корневая рабочая директория агентского цикла
2. файл конфигурации harness.json5

В сценарии №1 и №2, предполагается, что файл конфигурации уже есть в CWD и поэтому его остаётся только загрузить в UI клиента.
В сценарии №3 предполагается, что файл конфигурации отсутствует, т.к. третий режим, это ситуация когда агентский цикл запускается во временной рабочей директории, для выполнения каких-то локальных целей, а не в среде с продолжающейся работой на чем-либо. В этом случае необходимо создать файл конфигурации по умолчанию и загрузить его в UI.

В UI пользователь должен иметь возможность изменять файл конфигурации требуемым ему образом, каковые изменения должны отправляться на сервер перед следующим запуском агентского цикла.

Вообще пользователь должен иметь возможность взаимодействовать с файловой системой внутри CWD (создавать/изменять/удалять файлы/каталоги), чтобы иметь возможность управлять файлами для roles и skills, а также, возможно, вносить некоторые изменения в другие файлы внутри CWD. Для этого на стороне сервера должно быть предусмотрено минимальное базовое REST-API для работы с файловой системой, которая на стороне клиента уже будет, вероятно, обёрнута в определённые процессы (например: добавить файл роли, добавить файл умения, добавить агнета, и т.д.).
