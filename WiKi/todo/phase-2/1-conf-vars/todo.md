# Задача на разработку: Переменные `vars` в json5-конфигурации
Добавить в crate `conf` отдельный модуль `crates/conf/src/vars.rs`, который подставляет значения переменных в текст json5-файла **до** его парсинга, и подключить его ко всем местам, где `conf` читает json5 (файл цикла `harness.json5` и файл агента, например `grok-4.6.json5`).

Зачем: чтобы выносить повторяющиеся и «настраиваемые пользователем» значения (пути, лимиты, имя бинарника git) в одну секцию `vars` в начале файла. Это же основа для задачи 4 (шаблон конфигурации, где пользователь правит только `vars`).

Ожидаемый результат: файл вида
```json5
{
    "vars": {
        "test-var-1": "some substitution",
        "test-var-2": 3.14, // number
    },
    "key-1": "${vars:test-var-1} will be placed here",
    "key-2": ${vars:test-var-2}
}
```
(формально невалидный json5 до подстановки) успешно загружается: `key-1` = `"some substitution will be placed here"`, `key-2` = `3.14`.

## Функциональные требования
### 1. Секция `vars`
1. Необязательная секция верхнего уровня файла с ключом `vars` (константа `keys::VARS = "vars"` в `crates/conf/src/str/keys.rs`, литерал в коде не использовать).
2. Значение — json5-объект `{ "<var-name>": <json5-value> }`. Допустимые значения: строка, число, bool, `null`, массив, объект.
3. Имя переменной: символы `A-Z a-z 0-9 _ - .`, не пустое. Иначе — ошибка с именем и местом.
4. Секция может стоять в любом месте файла верхнего уровня, в том числе **после** первого использования переменной (поэтому подстановка двухпроходная).
5. Секция `vars` остаётся в тексте, парсится вместе со всем файлом и загрузчиками игнорируется (как любой неизвестный ключ). Каждый файл имеет **собственную** область переменных: переменные `harness.json5` не видны в файле агента и наоборот.
6. Внутри самой секции `vars` подстановки не поддерживаются: найденный там `${vars:...}` → ошибка `nested variables are not supported`.

### 2. Синтаксис использования
1. Распознаётся только точная форма `${vars:<var-name>}`. Любой другой текст `${...}` (например `${HOME}`, `${env:X}`) остаётся без изменений.
2. Подстановка допускается в любом месте файла, кроме секции `vars`: в значении-строке, в самом значении (без кавычек), в имени ключа внутри кавычек, в элементе массива.
3. Подстановка — чисто текстовая замена по ключу; тип значения определяется контекстом:
   | Контекст | Значение переменной | Результат |
   |---|---|---|
   | внутри строки `"..."` / `'...'` | строка | содержимое строки, **экранированное** под тип кавычек (`"`/`'`, `\`, переводы строк, управляющие символы), без добавления кавычек |
   | внутри строки | число / bool / `null` | текстовое представление (`3.14`, `true`, `null`) |
   | внутри строки | массив / объект | ошибка `only scalar values can be embedded into a string` |
   | вне строки (голое `${vars:x}`) | строка | json-строка с кавычками и экранированием: `"text"` |
   | вне строки | число / bool / `null` / массив / объект | компактный json-литерал |
4. В одной строке допускается несколько подстановок.
5. Текст в комментариях (`// ...` и `/* ... */`) **не обрабатывается**: подстановка не выполняется, неизвестная переменная в комментарии не является ошибкой. Для этого сканер текста должен различать состояния: код / строка в двойных кавычках / строка в одинарных кавычках / однострочный комментарий / блочный комментарий (с учётом `\`-экранирования внутри строк).
6. Экранирование самого `${vars:...}` не поддерживается (не реализовывать).

### 3. Ошибки (`ConfError`, понятный текст на английском)
Формат: `<file>:<line>: <error|warning> → <message>`. Обязательные случаи:
1. Неизвестная переменная: `error → variable '<name>' is being used but not defined`
2. Переменная, объявленная, но не использованная, — не ошибка, но должно выводиться предупреждение: `warning → variable '<name>' is defined but not used`.
3. `vars` не является объектом или не парсится как json5: `error → vars is not an json5-object`
4. Вложенная подстановка в `vars`; массив/объект внутри строки: `error → vars consists not only from simple types (string, num, bool)`
5. Ошибки парсинга json5 **после** подстановки сообщаются как сейчас (номера строк относятся к тексту после подстановки — это допустимо, указать в докстринге модуля).

### 4. API модуля и интеграция
1. `crates/conf/src/vars.rs`: докстринг модуля, одна точка входа, например
   `pub(crate) fn substitute(text: &str, source: &str) -> Result<String, ConfError>`
   (`source` — имя файла для сообщений об ошибках). Поиск секции `vars` — собственным сканером по тексту (до парсинга всего файла), сама секция затем разбирается `json5::from_str`.
2. Подключить в `crates/conf/src/load.rs` во всех местах, где вызывается `json5::from_str` для **файлов** (`load` для `harness.json5`, `read_model_object` для файла агента). Остальной код загрузки не менять.
3. `mod vars;` в `crates/conf/src/lib.rs`; публичный экспорт не нужен.
4. Новых зависимостей в `crates/conf/Cargo.toml` не добавлять (сканер пишется вручную). Если без зависимости не получается — остановись и спроси.
5. Файлы без секции `vars` и без `${vars:` должны загружаться ровно как раньше (обратная совместимость, текст не меняется).

## Scope
- `crates/conf/src/vars.rs` (создать)
- `crates/conf/src/load.rs`
- `crates/conf/src/lib.rs` (`mod vars;` + интеграционные тесты загрузки)
- `crates/conf/src/str/keys.rs` (константа `VARS`)

Не менять: `template.rs`, типы настроек, другие crates.

## Проверка корректности решения
1. `cargo test -p conf`, затем `cargo test --workspace`.
2. Unit-тесты в `vars.rs` (без обращения к сети и к реальным ключам):
   - пример из раздела «Ожидаемый результат» (строка, число вне строки);
   - таблица из п. 2.3 (все строки таблицы);
   - экранирование `"`, `\`, `\n` внутри строки; одинарные кавычки;
   - переменная после места использования;
   - подстановка в комментарии игнорируется (в т.ч. неизвестная переменная);
   - `${HOME}` и `${env:X}` остаются без изменений;
   - все ошибки из раздела 3 содержат имя файла и `line:col`;
   - файл без `vars` и без `${vars:` возвращается побайтово неизменным.
3. Интеграционные тесты в `lib.rs`: `harness.json5` с `vars` (подстановка лимитов, путей) и файл агента с `vars` (подстановка `api-key`/лимитов) успешно проходят `conf::load`; переменные не «протекают» между файлами (использование переменной из другого файла → ошибка `unknown variable`).
