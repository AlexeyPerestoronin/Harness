# Задача на разработку: Dump сессии, не зависящий от целевого агента
Сделать формат файла `dump.json` нейтральным к вендору, чтобы сессию, начатую одним агентом (например Claude Sonnet 5.5), можно было продолжить через `--dump` другим (например Grok 4.6 или Gemini).

Зачем: сейчас каждый агент пишет **собственный** формат dump (xAI: `conv_id/chat_id/usage_stats/messages` в формате OpenAI; Google: `usage_stats/history/pending_message` в формате Gemini `contents`; Claude: `messages/usage` в формате Anthropic) и читает только его. Продолжить сессию другим агентом нельзя — упирались в формат, а не в смысл диалога.

Анализ текущей логики (для справки, проверь по коду):
- `AgentLoop::start` при `--dump` вызывает `agent.reload_session(src)`, после каждой итерации — `agent.dump_session(dump_file)` в **новую** папку сессии.
- В dump не записана идентичность агента, поэтому ограничения «тот же вендор» формально нет, но форматы сообщений несовместимы (tool calls: OpenAI `tool_calls`+`role:tool`, Anthropic `tool_use`/`tool_result` блоки с `id`, Gemini `functionCall`/`functionResponse` **без id**; у Google ещё `pending_message` — результаты инструментов, ещё не отправленные модели).

Предусловие: желательно после задачи 5 (выбор агента из папки), но технически независима.

Ожидаемый результат: dump, записанный любым агентом, загружается любым другим агентом, и диалог продолжается корректно (история, вызовы и результаты инструментов сохранены и согласованы).

## Функциональные требования
### 1. Нейтральный формат (версия 2)
Новый модуль `crates/harness/src/agents/dump.rs` (структуры serde + конвертации). Файл `dump.json`:
```json
{
  "format": "harness-dump",
  "version": 2,
  "written-by": { "vendor": "Claude", "name": "Claude Sonnet 5.5" },
  "usage": [ { "vendor": "Claude", "name": "Claude Sonnet 5.5", "requests": 3, "input_tokens": 100, "output_tokens": 20, "cached_tokens": 0, "total_cost_usd": 0.0 } ],
  "messages": [
    { "role": "user", "text": "..." },
    { "role": "assistant", "text": "...", "tool_calls": [ { "id": "call_1", "name": "read_file", "arguments": { "path": "a.txt" } } ] },
    { "role": "tool", "results": [ { "call_id": "call_1", "name": "read_file", "content": "..." } ] },
    { "role": "assistant", "text": "done" }
  ]
}
```
1. `messages` — полная история диалога, **включая** хвостовые результаты инструментов, которые ещё не были отправлены модели (для Google это содержимое `pending_message`).
2. Роли: `user` (`text`), `assistant` (`text?`, `tool_calls?`), `tool` (`results[]`). Один `tool`-элемент соответствует одному набору результатов на один ход ассистента.
3. Вендорные «лишние» данные (reasoning у xAI, thinking-блоки/подписи у Claude, `thoughtSignature` и прочие служебные части Gemini) не входят в нейтральные поля. Чтобы **не терять** их при продолжении тем же вендором, каждое сообщение может нести необязательное поле `"native": { "vendor": "<vendor>", "payload": <исходное сообщение вендора как есть> }`. Агент того же вендора, встретив `native`, использует `payload` вместо реконструкции из нейтральных полей; агент другого вендора поле игнорирует.
4. `usage` — массив записей по агентам (кто сколько потратил), информационный. Правила продолжения см. п. 3.
5. Идентичность агента в `written-by` и `usage` — информационная; решение о совместимости по ней **не принимается**.

### 2. Конвертации
Каждый агент (`xai.rs`, `google.rs`, `claude.rs`) умеет `native → neutral` (в `dump_session`) и `neutral → native` (в `reload_session`); общие структуры и хелперы — в `dump.rs`. Внутреннее хранение истории в агентах (для запросов) можно оставить нативным.
1. **ID вызовов.** xAI и Claude требуют `id` вызова и согласованные результаты. У Gemini id нет: при `Google → neutral` id генерируются детерминированно (`call_<n>`, сквозная нумерация по сессии) и результаты сопоставляются с вызовами по порядку; при `neutral → Google` id отбрасываются, `functionResponse` строится по `name`, порядок сохраняется.
2. **Tool-результаты.** `tool` → xAI: по одному сообщению `role:tool` на каждый результат с `tool_call_id`; → Claude: одно `user`-сообщение с блоками `tool_result`; → Google: одно `user`-сообщение с `functionResponse`-частями.
3. **Хвост без ответа.** Если последний элемент `messages` — `tool` (результаты не отправлены) или `user` (промпт не отправлен), то для Google он загружается в `pending`, а для xAI/Claude остаётся последним сообщением истории — так следующий `iteration(None)` отправляет запрос корректно.
4. **Сообщение ассистента без текста** (только `tool_calls`) и текст без вызовов должны конвертироваться корректно во все стороны.
5. Содержимое результатов инструментов — строки; не изменять и не усекать.

### 3. Учёт расхода при продолжении
1. Если агент, загружающий dump, совпадает с последней записью `usage` по `(vendor, name)`, его счётчики **продолжаются** с её значений (как сейчас при продолжении тем же агентом — лимиты сессии кумулятивны).
2. Если агент другой, его счётчики стартуют с **нуля** (токены разных вендоров/токенайзеров несоизмеримы, лимиты относятся к новому запуску). Записи предыдущих агентов сохраняются в `usage` и дописываются в новый dump, новая запись добавляется для текущего агента.
3. В `log.md` новой сессии, помимо строки `- continue from dump: <path>`, добавить строку `- dump written by: <vendor> <name>`. Если агент отличается от `written-by`, добавить пометку `(different agent: history converted)`.
4. Статистика в `finish()` агентов — только по счётчикам текущего агента (формат вывода не менять).

### 4. Совместимость со старыми dump
1. Файл без поля `format` считается устаревшим (legacy) вендорным dump. Агент соответствующего вендора загружает его как раньше (старые структуры `XaiDump` / `GoogleDump` / `ClaudeDump` остаются только для чтения), все новые dump пишутся в формате v2.
2. Legacy dump **другого** вендора → ошибка с понятным текстом: `dump '<path>' has legacy <vendor> format; continue it with the same vendor first (a new dump will be written in the vendor-independent format) or ...`. Автоконвертация legacy между вендорами не требуется.
3. Определение вендора legacy-файла — по набору полей (`conv_id`/`chat_id` → xAI; `history` → Google; `messages` + `usage` без `conv_id` → Claude); тест на каждый вариант.
4. Неподдерживаемое значение `version` → ошибка `unsupported dump version`.

### 5. Мелочи
1. Для xAI `conv_id`/`chat_id` в нейтральный формат не пишутся: после загрузки генерируются новые (как при новой сессии).
2. Не менять логику HTTP-запросов, парсинг ответов и учёт токенов/стоимости.
3. Поведение при продолжении dump, который закончился ответом ассистента без вызовов инструментов (сессия уже завершена и `prompt` не передан), **не менять** и не расширять — отметить в `result.md` как наблюдение.

## Проверка корректности решения
1. `cargo test --workspace`. Реальные API и ключи не использовать (живые тесты `agents_live_tests` не запускать).
2. Unit-тесты на фикстурах (JSON-литералы в тестах):
   - `native → neutral → native` для каждого вендора без потерь по смыслу (текст, имена и аргументы вызовов, содержимое результатов); с `native.payload` — побайтово идентичное сообщение вендора;
   - кросс-конвертации по матрице 3×3 для сессии «user → assistant(tool_calls×2) → tool(results×2) → assistant(tool_calls) → tool(results)»: у результата для xAI/Claude каждый `tool_call_id`/`tool_use_id` соответствует вызову, порядок сохранён; для Google порядок `functionResponse` соответствует порядку `functionCall`;
   - Google с `pending_message` → нейтральный dump → Claude/xAI: хвост — результаты инструментов; Claude/xAI с хвостовыми результатами → Google: хвост загружен в `pending`;
   - счётчики: тот же агент продолжает, другой стартует с нуля, `usage` накапливает записи;
   - legacy dump своего вендора загружается; legacy другого вендора → ошибка; `version: 3` → ошибка;
   - формат v2 содержит `format`, `version`, `written-by`, `usage`, `messages`.
3. Ручной шаг (не обязателен): `dump.json` из каталога `.log/` (legacy Claude) продолжить тем же Claude, затем получившийся v2-dump — другим агентом, убедиться по логу, что история загружена.
