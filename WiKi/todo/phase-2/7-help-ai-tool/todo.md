# Задача на разработку: Tool `help` — развёрнутая справка по инструментам для AI (`help-ai.txt`)
Добавить модуль инструментов `crates/tools/src/help.rs` с tool'ом `help`, который по запросу агента возвращает подробную справку по доступным инструментам из файла `crates/tools/help-ai.txt`.

Зачем: описания в `ToolDescriptor` намеренно короткие (они уходят в каждый запрос и стоят токенов). Подробности — формат ответов, ограничения, типовые ошибки, примеры — агент запрашивает сам, только когда это нужно.

Предусловия: выполнены задачи 2–3 (параметры `available-files`, `deprecated-*` существуют и работают — справка должна их описывать).

Ожидаемый результат:
- в `harness.json5` можно включить модуль `"help": {}` (по общему правилу: нет ключа → модуль не регистрируется);
- агент вызывает `help({})` → получает оглавление (имена инструментов и по одной строке), `help({"tool": "find_str"})` → полный раздел про этот инструмент.

## Функциональные требования
### 1. Модуль и конфигурация
1. Новый модуль `crates/tools/src/help.rs` (`pub mod help;`, `Module::Help` в `crates/tools/src/lib.rs`), `HelpModule::descriptors()`, `HelpModule::call()` — по образцу `user.rs`.
2. Ключ модуля в `conf`: `keys::TOOL_HELP = "help"`; `HelpSettings {}` (пустая структура) в `types.rs`, поле `ToolsSettings.help: Option<HelpSettings>`, ветка в `load_tools` (`"help": {}` включает модуль). Модуль не имеет параметров.
3. `ToolRegistry::build` регистрирует `HelpModule`, если `settings.help.is_some()`.
4. `help.rs` не зависит от `Sandbox` и не обращается к файловой системе: текст вшит в бинарник.

### 2. Descriptor
1. Имя tool'а: `help`. Описание (EN): `Get detailed usage help for tools: no arguments → list of tools; with "tool" → full help for that tool.`
2. Параметры: `{"type":"object","properties":{"tool":{"type":"string"}}}` — `tool` необязательный. Параметры из `required` не добавлять (поддержка `{}` и отсутствия аргументов уже есть в `ToolRegistry::call`).

### 3. Файл `crates/tools/help-ai.txt`
1. Подключается `include_str!("../help-ai.txt")` в `help.rs` (аналогично `crates/harness/help.txt`), доступен как `pub const HELP_AI: &str`.
2. Язык — **английский** (текст для модели, как и описания tools).
3. Структура файла (чтобы `help.rs` мог разбирать разделы без новых зависимостей): краткое вступление, затем разделы, каждый начинается со строки-заголовка `## <tool_name>`. Вступление и все разделы разделяются строго по этому маркеру.
4. Раздел каждого tool'а содержит:
   - `Module:` модуль (`fs` / `git` / `terminal` / `user` / `help`);
   - `Purpose:` одна-две строки;
   - `Parameters:` имя, тип, обязательность, смысл, ограничения;
   - `Returns:` формат успешного ответа (дословные префиксы вроде `success: wrote <path>`, `available: [...]`, пустой ответ при отсутствии совпадений) и формат ошибки (`cannot <action> '<path>' → <reason>`);
   - `Examples:` 2–3 примера вызова (аргументы в JSON) с ожидаемым ответом;
   - `Notes:` ограничения и особенности (префиксы `r:`/`w:`, список расширений, deprecated-пути, таймауты, подтверждение пользователем и т.д.).
5. Охватить **все** инструменты всех модулей: `fs` (все 18 текущих), `git` (4), `terminal` (`run_shell`, `run_invoke`, `list_available_shell_commands`), `user` (4), `help`. Фактические форматы ответов, сообщения об ошибках и ограничения **сверять с кодом** модулей (`fs.rs`, `fs/search.rs`, `fs/access.rs`, `git.rs`, `terminal.rs`, `process.rs`, `user.rs`), а не придумывать.
6. Общий раздел вступления: как читать ошибки доступа (`access denied`, `path is deprecated`, `unavailable file extension`) и что делать в каждом случае (запросить доступ через `request_*_access_for` — не для deprecated; не повторять запрос для deprecated-пути).
7. Должна быть оговорка: набор доступных инструментов определяется конфигурацией; если инструмента нет в списке tools агента, значит модуль выключен.

### 4. Поведение `help`
1. Разбор `HELP_AI` на вступление и разделы по маркеру `## `, без сторонних crate.
2. Без аргумента `tool` (или пустая строка): вернуть вступление + оглавление: по строке `<tool_name> — <Purpose, первая строка>` для каждого раздела.
3. `tool = "<name>"`: вернуть полный раздел (заголовок + тело) для точного совпадения имени (регистр значим).
4. Неизвестное имя → ошибка (`cannot get help → unknown tool 'x'; available: a, b, c`). Результат ошибки возвращается агенту так же, как у остальных инструментов (через `Err(String)`).
5. Ответ — `CallResult::plain(...)`.
6. Справка **не фильтруется** по включённым модулям (это статический текст).

### 5. Шаблон конфигурации
В `crates/conf/settings-template.json5` добавить модуль `"help": {}` с комментарием (`Help tool for the agent: detailed usage of every tool (help-ai.txt)`). Если в шаблоне есть тест согласованности ключей — добавить `TOOL_HELP`.

Остальные модули `tools` — только чтение для сверки формата.

## Проверка корректности решения
1. `cargo test --workspace`.
2. Тесты в `tools`:
   - **согласованность справки**: для каждого имени из `descriptors()` всех модулей (`FsModule`, `GitModule`, `TerminalModule`, `UserModule`, `HelpModule`) в `HELP_AI` есть раздел `## <name>`; и наоборот — нет разделов с неизвестными именами;
   - в каждом разделе есть метки `Module:`, `Purpose:`, `Parameters:`, `Returns:`, `Examples:`;
   - `help({})` содержит имена всех инструментов; `help({"tool":"find_str"})` содержит раздел `find_str`; неизвестное имя → ошибка со списком;
   - реестр: при `help: Some` в `ToolRegistry::list()` есть `help`; при `None` — нет.
3. Тесты в `conf`: `"help": {}` включает модуль; шаблон по-прежнему проходит тесты.
4. Ручной шаг (не обязателен): включить `"help": {}` и попросить агента вызвать `help` для `write_file`.
