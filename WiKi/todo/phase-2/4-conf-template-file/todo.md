# Задача на разработку: Шаблон конфигурации в отдельном файле `settings-template.json5` с переменными `vars`
Вынести текст шаблона `--conf-new` из Rust-кода в файл `crates/conf/settings-template.json5` и переписать шаблон так, чтобы пользователю для окончательной настройки достаточно было править **только секцию `vars`**.

Зачем: сейчас текст шаблона собирается `format!` с десятками подстановок в `template_text()` — править его неудобно. Файл правится как обычный json5, а код отвечает только за вставку в бинарник и запись на диск.

Предусловия: выполнены задачи 1 (`vars`) и 2 (`available-files`, `deprecated-*`).

Ожидаемый результат: `harness.exe --conf-new my.json5` создаёт файл, в начале которого секция `vars` с комментариями, а ниже — полный закомментированный шаблон, где все значения, которые нужно менять, заданы как `${vars:<name>}`. Поведение CLI и защита от перезаписи не меняются.

## Функциональные требования
### 1. Файл шаблона
1. Создать `crates/conf/settings-template.json5` — это полный текст шаблона (с комментариями), **без** Rust-плейсхолдеров `{...}`.
2. Подключать в код только через `include_str!("../settings-template.json5")` (путь относительно `crates/conf/src/template.rs`), аналогично `crates/harness/help.txt`.
3. `template.rs` после изменения: `template_text() -> String` возвращает содержимое файла как есть (без `format!`), `write_new_conf(path)` — как раньше (ошибка `already exists`, создание родительских каталогов). Сигнатуры публичных функций и экспорт в `lib.rs` не менять.
4. Из `crates/conf/src/str/keys.rs` удалить константы `PLACEHOLDER_*` и `DEFAULT_*`, которые после выноса текста никем не используются (проверить поиском по workspace; `DEFAULT_LOG_FOLDER` используется загрузчиком — оставить). Модульный докстринг `keys.rs` и `template.rs` обновить: шаблон больше не собирается из `keys`.

### 2. Содержание шаблона
1. Секция `vars` — **первая** в файле, с комментарием-инструкцией: «Edit only this section». Каждая переменная имеет комментарий, что это и в каком формате вводить.
2. Все значения, которые пользователь обязан задать, — переменные: путь рабочей области (`cwd`), путь к конфигурации агента (`agent-setting.config`), исполняемый файл git, рабочая директория/файл для `tools.fs` и `tools.terminal.cwd-list`. Лимиты сессии (`token-limit`, `iteration-limit`, `USD-limit`), `mode`, `log-folder`, таймауты также вынести в переменные со значениями по умолчанию — они тоже «настройки пользователя». Имена переменных — короткие kebab-case (`workspace`, `agent-config`, `git-executable`, `work-dir`, `token-limit`, ...), использовать каждую переменную хотя бы один раз.
3. Остальное содержимое — готовые значения по умолчанию, пользователю менять не требуется (структура модулей, имена ключей, `available-file-extensions: []`, `deprecated-dirs: [".git", "target"]`, `deprecated-files: []`, список `available-commands`).
4. В шаблоне присутствуют все модули `fs`, `git`, `terminal`, `user` и все параметры `tools.fs`, включая `available-files`, `deprecated-dirs`, `deprecated-files` (с комментариями: что значит, пути без `r:`/`w:`, относительные пути считаются от текущей директории процесса, пересечение с `available-*` — ошибка при загрузке). Комментарии, описывающие инструменты (`find_str`, `list_available_shell_commands` и т.д.), сохранить.
5. Значения-числа в `vars` задаются числами (`128000`, `0.5`), а не строками; подстановка — вне строки (`"token-limit": ${vars:token-limit}`). Значения-пути — строками; подстановка внутри строки (`"w:${vars:work-dir}"`).
6. После подстановки всех переменных шаблон — валидный json5-объект, из которого `conf::load` читает ровно те же ключи, что и раньше (структура настроек не меняется).
7. Документировать в комментарии, что `agent-setting.config` указывает на файл агента (расширение до папки — задача 5).

### 3. Согласованность шаблона и кода
Так как ключи теперь написаны в файле, а не берутся из `keys`, добавить тест согласованности: каждая константа ключа, которую читают загрузчики (`keys::CWD`, `PATHS`, `LOG_FOLDER`, `AGENT_SETTING`, `CONFIG`, `MODE`, `TOKEN_LIMIT`, `ITERATION_LIMIT`, `USD_LIMIT`, `TOOLS`, `TOOL_*`, `AVAILABLE_*`, `DEPRECATED_*`, `EXECUTABLE`, `EXECUTION_LIMIT`, `CWD_LIST`, `AVAILABLE_COMMANDS`, `COMMAND_EXECUTION_LIMIT`, `INVOKE_EXECUTION_LIMIT`), присутствует в шаблоне как `"<key>"`.

## Scope
- `crates/conf/settings-template.json5` (создать)
- `crates/conf/src/template.rs`
- `crates/conf/src/str/keys.rs` (удаление неиспользуемых констант)
- `crates/conf/src/lib.rs` (тесты)
- `crates/harness/help.txt` — только если в описании `--conf-new` есть устаревшие утверждения (иначе не менять)

Не менять `load.rs` и `vars.rs`.

## Проверка корректности решения
1. `cargo test --workspace`.
2. Тесты в `conf`:
   - `write_new_conf`: создаёт файл, повторный вызов → `already exists`, создаёт родительские каталоги (существующие тесты);
   - шаблон проходит `vars::substitute` и затем `json5::from_str` в объект с ключами верхнего уровня `vars`, `cwd`, `paths`, `agent-setting`, `tools`;
   - каждая переменная секции `vars` используется в шаблоне; каждая используемая переменная объявлена;
   - тест согласованности ключей из раздела 3;
   - заменив значения `vars` на реальные (tmp-каталог, tmp-файл агента с литеральным ключом), шаблон загружается через `conf::load`.
3. Ручной шаг: `harness.exe --conf-new %TEMP%\t.json5` и визуальная проверка файла.
