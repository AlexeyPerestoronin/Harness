# Consulting 1 — Phase 7. REST API

## Область действия
Phase-7 не добавляет новых HTTP-эндпоинтов и не меняет формат существующих
DTO. Изменения касаются только **семантики валидации конфигурации** в
server-режиме `harness.exe --serve`.

## Затрагиваемые эндпоинты

### `GET /api/v1/config`
- Возвращает текущий конфиг.
- Поведение меняется косвенно:
  - в шаблоне/конфиге больше нет поля `cwd`;
  - `valid: true` означает, что конфиг прошёл новую валидацию CWD first
    (все пути внутри CWD, `agent.config` внутри CWD и т.д.).
- Контракт ответа (`path`, `exists`, `text`, `valid`, `validation_error`)
  не меняется.

### `PUT /api/v1/config`
- Валидация передаваемого текста должна использовать новую модель CWD:
  - `cwd` в теле конфига не допускается (или игнорируется — решение за
    реализацией, но рекомендуется считать неизвестным ключом и возвращать
    `CONFIG_INVALID`);
  - все относительные пути в конфиге проверяются относительно CWD сервера;
  - пути, выходящие за пределы CWD, отклоняются.
- Сохранение и перезагрузка конфига остаются прежними.
- Возможен нюанс: сервер стартует с CWD, заданным через `--cwd` или process
  cwd, поэтому `PUT /api/v1/config` не может изменить CWD — это ожидаемое
  поведение.

### `POST /api/v1/config/default`
- Создаёт `harness.json5` из шаблона, если файл отсутствует.
- Шаблон после phase-7 не содержит `cwd`; поведение эндпоинта не меняется.

## Рекомендации
- Отдельные REST-исследования не требуются.
- В `harness-api` (DTO) изменения не нужны.
- В тестах серверного режима добавить кейсы:
  - конфиг с путём вне CWD → `CONFIG_INVALID`;
  - конфиг без `cwd` → валиден;
  - `--conf` вне CWD → сервер не стартует.
