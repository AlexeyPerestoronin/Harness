## 1. Что хорошо

1. **Точный as-is анализ.** Описание текущего поведения совпадает с кодом:
   - `cwd` действительно обязателен и резолвится относительно `conf_dir`
     (`crates/conf/src/load.rs`, `resolve_cwd` / `resolve_cwd_path`);
   - `run_observed_command` действительно всегда собирает и возвращает весь
     stdout+stderr (`crates/tools/src/process.rs`);
   - `deprecated-dirs` — точные строки с матчингом по компонентам
     (`crates/tools/src/fs/access.rs`);
   - release job уже существует и использует `softprops/action-gh-release@v2`
     (`.github/workflows/ci.yml`).
2. **CWD first спроектирован в правильном направлении.** Единственный источник
   истины — процесс запуска; проверка «внутри CWD» по компонентам, а не по
   строке; лексическая нормализация `.` / `..`; учёт Windows case-insensitivity.
   Это соответствует запросу PO и убирает реальную неоднозначность текущей
   модели.
3. **Output buffer — минимально инвазивно.** Обрезка применяется только к
   строке, возвращаемой агенту; полный стриминг в консоль человека сохраняется.
   Опциональность аргумента с default `-1` даёт обратную совместимость.
   Единица «Unicode-символы» выбрана осознанно и соответствует формулировке PO.
4. **Glob вместо сырого regex — верное решение.** Примеры PO (`**/log`,
   `**/done`, `**/note-*`) действительно являются glob-паттернами; сырой Rust
   regex их не примет. Предложенная проверка ancestors (путь и все родительские
   каталоги) корректна и закрывает `walk_folder`, `list_folder` и
   `request_*_access_for`.
5. **REST API и UI не перегружены.** Консультант справедливо не вводит новые
   эндпоинты и не трогает `web-harness`; DTO не меняются.
6. **Релизный пайплайн не переизобретается.** Доработка существующего `ci.yml`
   дешевле и надёжнее, чем отдельный workflow или переход на `gh` CLI.
7. **Диаграммы в целом корректны.** Mermaid-схемы синтаксически валидны и
   отражают реальные потоки: `run_shell -> TerminalModule ->
   run_observed_command`; `tools.fs` Sandbox; CI → artifacts → release job.
   Логических тупиков не обнаружено.

## 2. Что плохо

Ниже — критические пробелы, из-за которых концепт в текущем виде нельзя
передавать в планирование задач.

### 2.1. Пропущены call-site'ы нового `load_server_config(conf_path, cwd)`

`arch.md` меняет сигнатуру `conf::load_server_config` на
`load_server_config(conf_path, cwd)`, но в сводной таблице изменений указан
только `cli-harness/src/server/mod.rs`. При этом фактически
`load_server_config` вызывается ещё в **пяти местах**
`crates/cli-harness/src/server/config.rs`:
`get_config`, `config_default`, `validate_config_text`,
`reload_server_config`, `refresh_server_config` (плюс `read_existing_parsed`).

Без обновления `server/config.rs` и без хранения CWD в `ServerState` /
`LoadedServerConfig` (сейчас поле `cwd` там отсутствует) проект **не
скомпилируется** после изменения сигнатуры. Это не «мелочь реализации», а
пропущенный архитектурный узел: REST-слой должен знать CWD сервера, в том
числе когда конфиг невалиден и `settings == None`.

**Как исправить:** добавить в план:
- `crates/cli-harness/src/server/state.rs` — хранить эффективный CWD сервера;
- `crates/cli-harness/src/server/config.rs` — прокидывать CWD во все вызовы
  `load_server_config` / `validate_config_text`.

### 2.2. Противоречие в default conf path для консольного режима

`arch.md` (раздел 3.2, `cli.rs`) утверждает:
> `default_conf_path()` остаётся `<process-cwd>/harness.json5`; с учётом
> `--cwd` это будет `<CWD>/harness.json5`.

Это неверно для текущего кода: `parse_args` в `cli.rs` для консольного
`Start` использует `conf.unwrap_or_else(default_conf_path)`, а
`default_conf_path()` **не знает** про `--cwd` и всегда использует process cwd.
В server-режиме учёт `--cwd` уже есть (`default_conf_path_for_serve`), а в
консольном — нет.

Следствие: `harness --cwd D:\work --prompt "..."` без `--conf` будет искать
`<process-cwd>\harness.json5`, а не `<CWD>\harness.json5`, и при новом правиле
«conf обязан быть внутри CWD» упадёт с ошибкой. Это прямое противоречие цели
«CWD first».

**Как исправить:** зафиксировать, что `default_conf_path` вычисляется от
эффективного CWD в обоих режимах (например, `default_conf_path(cwd)`), и
внести `cli.rs` / `parse_args` в сводную таблицу изменений.

### 2.3. `server.tls-cert` / `server.tls-key` не покрыты CWD first

To-be гласит: «Любой путь из `harness.json5` (относительный или абсолютный)
после нормализации обязан находиться внутри CWD». Но в перечне путей, которые
проводятся через `resolve_in_cwd`, **нет** `server.tls-cert` и
`server.tls-key`.

Сейчас `crates/conf/src/load.rs` читает их как строки без резолва
(`parse_tls_path`), а `crates/cli-harness/src/server/tls.rs` использует «как
есть». После phase-7 относительный `tls-cert` будет вести себя иначе, чем
остальные пути конфига, либо (если формально применить правило) сертификаты,
лежащие вне рабочей директории (обычная практика), станут ошибкой загрузки.
Оба варианта должны быть осознанным решением, а не умолчанием.

**Как исправить:** явно указать в `arch.md`/`base.md`: TLS-пути резолвятся
относительно CWD и проверяются на «внутри CWD», **либо** они являются
исключением из правила (рекомендуется) — и это исключение зафиксировать в
документации и тестах.

### 2.4. `api-key` в model-файлах не рассмотрен

Аналогичная дыра: `conf::load.rs` (`resolve_api_key_value`) резолвит
относительный путь к файлу с API-ключом относительно **process cwd**, а не
CWD и не каталога model-файла. Консультация нигде не говорит, как этот путь
должен вести себя в модели «все относительные пути внутри CWD».

**Как исправить:** либо явно включить `api-key`-пути в новую модель резолва,
либо явно объявить их исключением (секрет может лежать вне CWD). Умолчание
недопустимо: это источник неоднозначности и потенциальной утечки/отказа.

### 2.5. Рекомендация «cwd = неизвестный ключ» нереализуема без доп. изменения

`api.md` рекомендует при `PUT /api/v1/config` считать `cwd` неизвестным ключом
и возвращать `CONFIG_INVALID`. Но текущие загрузчики **не валидируют корневые
ключи** `harness.json5`: `load_from_value` и `server_settings_from_value` не
вызывают `reject_unknown_keys` для корня (`server` — да, `fs`/`terminal`/`git`
— нет, корень — нет). То есть сегодня `cwd` в конфиге просто игнорировался бы.

Чтобы выполнить рекомендацию, необходимо добавить корневую валидацию
`vars` / `server` / `agent` / `tools` и отклонить всё прочее. Это отдельное
изменение поведения, и оно не указано в сводной таблице.

**Как исправить:** выбрать один вариант и провести его через план:
- либо «`cwd` игнорируется» (меньше кода, но молчаливая деградация),
- либо «`cwd` — ошибка загрузки» (требует корневого `reject_unknown_keys`,
  добавить в `conf/src/load.rs` + тесты).

### 2.6. Не определена регистронезависимость glob-паттернов на Windows

`tech.md` говорит: «Регистронезависимость и слэши должны быть учтены тестами»,
но не определяет механизм. Существующие `deprecated-dirs` регистронезависимы
на Windows через `comparable_parts` (`crates/tools/src/fs/access.rs`). Новые
паттерны без явного `(?i)`/lowercase-сравнения будут регистрозависимыми, т.е.
`**/Log` не запретит `log` на Windows. Это расхождение с существующей
семантикой денylist'а.

**Как исправить:** зафиксировать: на Windows regex компилируется как
case-insensitive (или сравнение идёт по нормализованному lowercased пути), на
Unix — как case-sensitive. Добавить тесты.

### 2.7. Грамматика паттернов не доопределена

Спецификация свелась к трём примерам и таблице трансляции. Правило
«заменять `**/` на `(?:^|.*/)?`» из `arch.md` (5.2) может давать иные
результаты, чем компонентная форма `(?:^|/)component(?:/|$)`, для паттернов
типа `**/log/**`, `log/**`, `**/note-*/*` и т.п. Не определён поддерживаемый
набор: только `**/<component>`? Разрешён ли `*` в середине компонента?
Как трактуется `foo/**/bar`?

Для реализации это означает дрейф между `conf` (валидация) и `tools`
(матчинг) и непредсказуемое поведение для пользователя.

**Как исправить:** зафиксировать строгое подмножество glob-синтаксиса,
достаточное для PO-примеров (рекомендуется: `**/<component>` + `*` внутри
компонента), и описать трансляцию единой функцией с тестами. Всё, что вне
подмножества, — ошибка конфигурации.

### 2.8. Сводная таблица изменений неполна

Помимо `server/config.rs` и `state.rs` (п. 2.1), в таблице не отражены:
- `crates/cli-harness/src/cli.rs` в части `default_conf_path` для консольного
  режима (п. 2.2);
- корневой `harness.json5` проекта (упомянут в рисках, но не в таблице);
- тесты конфигурации/песочницы (unit-тесты для `resolve_in_cwd`,
  glob-трансляции, Windows case-insensitivity);
- возможное обновление `Cargo.lock` после добавления `regex` в `conf`.

### 2.9. Release: несостыковка именования Windows-артефакта

To-be задаёт имя `harness-<version>-windows.exe`, но сейчас CI job
(`ci.yml`, шаг `Artifact name and path`) загружает Windows-артефакт как
`harness-<version>.exe`, а release job скачивает именно его. Если поменять
только release-ассет, download-artifact упадёт; если поменять только upload —
release job будет искать старый артефакт.

**Как исправить:** явно указать, что меняются **оба** шага: `ci` (upload
artifact name) и `release` (download artifact name + итоговое имя ассета).
Заодно зафиксировать правило ограничения release-триггера (`v*` vs
`harness-*` vs любой тег), потому что сейчас `if: startsWith(github.ref,
'refs/tags/')` создаёт релиз для любого тега.

## 3. Что можно улучшить

1. **Output buffer: не копировать весь вывод в `Vec<char>`.**
   `tail_chars(s, n)` можно реализовать как `s.chars().rev().take(n)` с
   последующим разворотом — без полного сбора всех символов в Vec. Это не
   критично, но дёшево и снижает пиковое потребление памяти на больших логах.
   Если хочется полностью выполнить PO-семантику «буфер вытесняет старые
   значения», можно рассмотреть bounded ring-buffer при чтении; впрочем, для
   phase-7 это уже YAGNI — достаточно текущей модели с пометкой об ограничении.

2. **Валидировать `output_buff_size`.** В schema указать явно: integer,
   `-1` или `>= 0`; значения меньше `-1` и нецелые должны давать ошибку tool
   call, а не молча трактоваться как `-1`. Добавить helper `arg_i64` с такой
   проверкой.

3. **`PUT /api/v1/config`: передавать CWD в `validate_config_text` явно.**
   Сейчас функция валидирует через временный файл. После CWD first стоит
   прокидывать в неё CWD сервера из состояния, а не полагаться на process cwd
   или на то, что `settings` непустой.

4. **Симлинки / junction'ы.** Проверка «внутри CWD» лексическая и не защищает
   от выхода через symlink/junction. Для native-утилиты это известное
   ограничение; если phase-7 не вводит canonicalization, стоит явно
   зафиксировать это как принятый риск (и не обещать «строгую изоляцию» в
   документации).

5. **Release notes.** Выбрать один источник: `generate_release_notes: true`
   либо `body` из `CHANGELOG.md`. Сейчас `arch.md` предлагает оба через «либо»;
   для планирования задач нужно одно решение (рекомендуется
   `generate_release_notes: true` как MVP).

6. **Тесты.** Дополнительно к уже предложенным: тест «конфиг без `cwd`
   валиден», «`--conf` вне CWD не стартует», «`deprecated-dir-patterns` не
   пропускает обход `walk_folder`», «путь с `..` выше CWD отклоняется».
   Это дёшево и закрывает основные регрессии.

## 4. Итоговый вердикт

**Отправить на доработку Project Consultant.**

Концепция жизнеспособна, направление правильное, и большинство решений
соответствуют KISS/YAGNI. Однако в текущем виде план содержит критические
пробелы полноты, из-за которых он не готов к передаче в Project Analyst /
Senior Developer:

- пропущены обязательные call-site'ы `load_server_config` в REST-слое
  (`server/config.rs`, `state.rs`) — проект не соберётся;
- противоречие в default conf path для консольного режима с `--cwd`;
- не покрыты `tls-cert` / `tls-key` и `api-key`-пути в модели CWD first;
- рекомендация «`cwd` = unknown key» не обеспечена корневой валидацией;
- не специфицирована Windows case-insensitivity и грамматика glob-паттернов;
- несостыковка именования Windows-артефакта в release job.

**Необходимые действия перед утверждением:**
1. Project Consultant дорабатывает `arch.md`, `api.md`, `tech.md` и сводную
   таблицу изменений по пунктам раздела 2.
2. После доработки — повторный короткий design review (design-review-2) только
   по изменённым разделам; полное перечитывание не требуется, если правки
   будут точечными.

До закрытия этих пунктов начинать планирование задач фазы 7 не рекомендуется.
