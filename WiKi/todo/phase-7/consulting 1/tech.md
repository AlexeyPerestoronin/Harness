## 2. CWD first — технические решения

### 2.1. Каноническая форма пути
- Все пути приводятся к абсолютному нормализованному виду:
  - `.` — пропускается;
  - `..` — снимает последний компонент;
  - разделители `\` и `/` считаются эквивалентными.
- Проверка «внутри CWD» — по компонентам пути (`starts_with`), а не по строке,
  чтобы `C:\work` не считался внутри `C:\work2`.
- На Windows сравнение компонентов регистронезависимое.

### 2.2. Где применяется резолв
| Источник пути | Старое поведение | Новое поведение |
|---|---|---|
| `agent.config` | от `conf_dir` | от `cwd`, проверка внутри `cwd` |
| `tools.fs.*` | от `settings.cwd` (который брался из json5) | от `cwd`, проверка внутри `cwd` |
| `tools.terminal.cwd-list` | от `settings.cwd` | от `cwd`, проверка внутри `cwd` |
| `skills.*.file`, `roles.*.file` | от `conf_dir` | от `cwd`, проверка внутри `cwd` |
| `--conf` | от process cwd | от process cwd, затем проверка внутри `cwd` |

### 2.3. Почему убираем `cwd` из json5
- `harness.exe` должен запускаться из любого места системы как обычная
  утилита (`PATH`), а рабочая директория должна задаваться местом запуска
  или явным `--cwd`.
- Единственный источник истины для CWD — процесс запуска, а не файл.
- Это убирает неоднозначность: раньше `cwd` зависел от того, где лежит
  конфиг, а не от того, откуда вызван процесс.

### 2.4. Совместимость с dump
- В dump больше не сохраняется `cwd`; при возобновлении CWD снова берётся из
  `--cwd` или process cwd.
- `settings.source` в dump сохраняется без `cwd`; пути в нём при возобновлении
  резолвятся от нового CWD.

## 3. Output buffer — технические решения

### 3.1. Единица измерения
- Использовать **Unicode-символы** (`chars`), а не байты: требование говорит
  о «количестве символов», и это интуитивно для модели.
- Реализация: `s.chars().collect::<Vec<_>>()`, взять последние `N`.
  Для очень больших выводов можно обойтись без полного сбора в Vec,
  но KISS: объёмы вывода, возвращаемые агенту, уже ограничены буфером.

### 3.2. Где обрезать
- Обрезать только строку, возвращаемую агенту. Потоковая печать в консоль
  пользователя остаётся полной — человек видит всё, модель получает хвост.
- Это минимально инвазивно: `process::run_observed_command` продолжает
  собирать и декодировать весь вывод, а обрезка применяется в самом конце.

### 3.3. Поведение граничных значений
| `output_buff_size` | Поведение |
|---|---|
| `-1` | весь вывод |
| `0` | пустая строка (либо `(output hidden)` — на выбор реализации) |
| `N > 0` | последние `N` символов |

### 3.4. Schema и совместимость
- `output_buff_size` — `type: "integer"`.
- Рекомендуется делать его опциональным с default `-1`:
  - старые вызовы не ломаются;
  - модель может не передавать его, когда объём не важен;
  - меньше строгости, но соответствует YAGNI.
- Если Project Owner хочет гарантированно осознанный выбор — сделать
  `required`; это trade-off (строже, но менее обратносовместимо).

## 4. RegExp / patterns for Deprecated-Dirs — технические решения

### 4.1. Почему glob, а не «сырой» regex
- Примеры PO (`**/log`, `**/done`, `**/note-*`) являются glob-паттернами.
- Сырой Rust `regex` не примет `**/log` без адаптации.
- Трансляция glob → regex проще для конечного пользователя и не требует
  знания regex.

### 4.2. Трансляция (концепт)
- Нормализовать паттерн: слэши `/`, без ведущего слэша.
- `**/` в начале → «любой префикс пути, заканчивающийся слэшем, либо его
  отсутствие».
- `*` внутри компонента → `[^/]*`.
- Литералы экранировать через `regex::escape`.
- Итоговый regex применяется к относительному нормализованному пути целиком;
  дополнительно проверяются ancestor-пути.

### 4.3. Валидация
- Паттерны компилировать при загрузке конфига в `conf`:
  - быстрый фидбек «конфиг невалиден» до запуска цикла;
  - в `tools` повторно компилировать не нужно (можно передавать готовые
    строки и кэшировать `Regex` в `Sandbox`).
- Для этого в `conf/Cargo.toml` добавить `regex = "1"`.

### 4.4. Матчинг путей
- Для проверяемого абсолютного пути получить относительный путь от `root`
  (`Sandbox.root`) в нормализованном виде.
- Для директории `a/b/log` проверить `a`, `a/b`, `a/b/log`.
- Для файла `a/b/log/x.md` проверить `a`, `a/b`, `a/b/log`, `a/b/log/x.md`.
- Если любой из них матчится — путь deprecated.

### 4.5. Производительность
- Число паттернов невелико (единицы), компиляция однократная.
- `Regex::is_match` на коротких строках дёшев.
- В `walk_folder` проверка перед рекурсией не допускает обход запрещённых
  поддеревьев.

## 5. GitHub release action — технические решения

### 5.1. Существующий стек
- `actions/checkout@v4`
- `dtolnay/rust-toolchain@stable`
- `actions/upload-artifact@v4` / `actions/download-artifact@v4`
- `softprops/action-gh-release@v2`

Этого достаточно; менять инструменты не требуется.

### 5.2. Доработки
- Чтение версии из `Cargo.toml` уже есть; добавить сверку с `github.ref_name`.
- `generate_release_notes: true` использует нативный механизм GitHub —
  не нужно вручную собирать changelog.
- `sha256sum` доступен на ubuntu из коробки; на Windows-раннере для
  контрольных сумм можно использовать `Get-FileHash` (если считать там) или
  считать все суммы в ubuntu `release` job после скачивания артефактов.
- Загрузка ассетов: `files: release/*` уже используется; расширить маской
  `release/*` (включая `.sha256`).

### 5.3. Почему не `gh release create`
- `softprops/action-gh-release` уже стоит и покрывает сценарий.
- Меньше shell-кода, декларативная конфигурация, проще поддерживать.
- `gh` CLI имеет смысл, только если понадобится нестандартная логика
  (например, редактирование существующего релиза).

## 6. Риски и ограничения
1. **Изменение семантики CWD ломает существующие конфиги.** Нужно обновить
   `settings-template.json5`, `help.txt`, `help-user.txt` и текущий
   `harness.json5` в корне проекта.
2. **Абсолютные пути вне CWD.** Требование «одна директория — свои конфиги»
   означает, что такие пути должны быть ошибкой. Это может затронуть
   пользователей, привыкших к глобальным путям (например, `C:/...`).
3. **Regex-паттерны и Windows.** Регистронезависимость и слэши должны быть
   учтены тестами.
4. **Output buffer и Unicode.** Обрезка по символам, а не по байтам, чтобы
   не рвать UTF-8.
5. **Release job зависит от артефактов CI.** Если CI частично упал, релиз не
   должен создаваться; текущая связь `needs: ci` это обеспечивает.
