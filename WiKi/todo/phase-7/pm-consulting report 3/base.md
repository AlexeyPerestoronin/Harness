# Consulting 3 — Phase 7. Базовое заключение

## Цель фазы
Доработать серверную (native) часть `cli-harness`:

1. **CWD first** — превратить `harness.exe` в системную утилиту, у которой
   рабочая директория задаётся не в конфиге, а внешним контекстом запуска.
2. **Output buffer for shell commands** — дать агенту контроль над объёмом
   возвращаемого вывода `run_shell` / `request_command_shell_execution`.
3. **Deprecated-dir-patterns** — добавить гибкий запрет директорий/файлов
   в `tools.fs` по glob-паттернам вида `**/log`, `**/done`, `**/note-*`.
4. **GitHub release action** — публикация получаемых на GitHub Actions
   дистрибутивов через `Create GitHub Release`.

## Зафиксированные решения по спорным точкам

| № | Развилка | Решение |
|---|---|---|
| 1 | `tools.git.executable`: путь конфига или внешняя команда? | **Внешняя команда/исполняемый файл.** Значение передаётся в `Command::new` как есть, не резолвится от CWD и не проверяется на «внутри CWD». Обычное значение `"git"` ищется в `PATH`. Это осознанное исключение из правила «все пути внутри CWD». |
| 2 | Число call-site'ов `load_server_config` в `server/config.rs` | **Шесть**: `get_config`, `config_default`, `validate_config_text`, `read_existing_parsed`, `reload_server_config`, `refresh_server_config`. |
| 3 | Константы ключей конфигурации | В `conf/src/str/keys.rs` добавляется `deprecated-dir-patterns`; ключ `cwd` остаётся как константа отвергаемого корневого ключа с обновлённой документацией. |
| 4 | Публичная `conf::load_model` | **Удаляется.** Внутри workspace вызовов нет; старую логику не храним. Внутренние функции `settings_from_model` / `settings_from_model_for_run` остаются, но получают CWD для резолва `api-key`. |
| 5 | Валидация имён release-артефактов | Используется строгий regex, который допускает только целевые имена и legacy Windows-артефакт: `^harness-[0-9]+\.[0-9]+\.[0-9]+(-linux|-macos|\.exe|-windows\.exe)$`. Несуществующие комбинации (`-windows` без `.exe`, `-linux.exe`, бессуффиксное имя) отклоняются. |
| 6 | Совместимость с dump-файлами phase ≤6 | **Обратная совместимость не требуется.** Старый dump с `settings.cwd` или без верхнеуровневого `"CWD"` — ошибка запуска. Логику `conf_dir_of` удаляем. |
| 7 | CWD при возобновлении из dump | Dump-файл содержит верхнеуровневый ключ `"CWD"` с фактическим CWD сессии. Запуск из dump требует только `--dump`; `--cwd` с `--dump` не комбинируется. |
| 8 | `Sandbox::from_fs` и компиляция regex | `Sandbox::from_fs` становится fallible (`Result`). Инвариант: `conf` валидирует и компилирует паттерны при загрузке конфига, поэтому в штатном цикле ошибка невозможна; fallible-сигнатура защищает от ручного вызова с невалидными паттернами. |
| 9 | Метасимволы glob | Поддерживается строгий синтаксис `**/<component>`; единственный wildcard — `*`. Символы `?`, `[`, `]` и прочие regex-метасимволы трактуются как литералы (экранируются). Ошибка валидации содержит конкретную позицию и список доступных метасимволов/синтаксис. |
| 10 | База для относительных `--conf` / `--dump` | Оба разрешаются от **process cwd** (как это делает ОС при открытии файла), затем нормализуются. `--conf` дополнительно обязан оказаться внутри CWD. `--dump` не проверяется на «внутри CWD»: CWD становится известен только после чтения dump. |
| 11 | Порядок проверок в `load_server_config` | Сначала `ensure_conf_in_cwd`, затем чтение/парсинг. `--conf` вне CWD при отсутствующем файле возвращает ошибку запуска, а не `Missing`. |
| 12 | `LoadedServerConfig.path` | Всегда абсолютный нормализованный путь; `resolve_conf_path` / `session::resolve_abs_path` вызываются до загрузки. |

## Что имеем (as-is)

### Общая структура
- Rust workspace: `crates/{cli-harness, conf, tools, agent-loop, interactions,
  logger, harness-api, auth, web-harness}`.
- `conf` — единственный крейт, который читает `harness.json5` и model-файлы;
  наружу отдаёт типизированные настройки.
- `tools` — реестр инструментов: `fs`, `git`, `terminal`, `user`, `skills`, `roles`.
- `cli-harness` — консольная точка входа и HTTPS-сервер (`--serve`).
- CI/CD: `.github/workflows/ci.yml` содержит job `ci` и job `release`.

### CWD (текущее поведение)
- Ключ `cwd` — обязательное поле `harness.json5`; относительный `cwd`
  резолвится относительно каталога конфига (`conf_dir`).
- `--cwd` работает как override значения из конфига и тоже резолвится
  относительно `conf_dir`.
- `agent.config`, `skills.*.file`, `roles.*.file` резолвятся относительно
  `conf_dir`; `tools.fs.*` и `tools.terminal.cwd-list` — относительно
  `settings.cwd`.
- Корневые ключи `harness.json5` не валидируются.
- `server.tls-cert` / `server.tls-key` читаются как строки без резолва.
- `api-key` в model-файлах резолвится относительно process cwd.
- `tools.git.executable` передаётся в `Command::new` как есть.
- Публичная `conf::load_model` существует, но в workspace не вызывается.

### run_shell / request_command_shell_execution
- `run_observed_command` всегда возвращает весь stdout+stderr, одновременно
  стримя его в родительскую консоль.
- У агента нет способа запросить только хвост вывода.

### tools.fs deprecated-*
- `deprecated-dirs` — точные строки, матчинг по компонентам абсолютного пути.
- Нельзя задать «любой каталог `log` на любом уровне вложенности».

### Dump
- Dump содержит верхнеуровневый `"settings"` с конфигом сессии.
- `cwd` хранится внутри `settings`; при возобновлении `conf_dir_of` вычисляет
  `conf_dir` из `agent.config`, а CWD берётся из `--cwd` или process cwd.

### GitHub Actions
- Windows-артефакт называется `harness-<version>.exe`; целевое имя ассета —
  `harness-<version>-windows.exe`.
- `release` job создаёт релиз для любого тега и не сверяет версию тега
  с `Cargo.toml`.

## К чему хотим прийти (to-be)

### CWD first
1. `cwd` полностью исключён из `harness.json5` и из `settings` внутри dump.
   Попытка задать `cwd` в конфиге — ошибка загрузки с отдельным сообщением.
2. CWD берётся из:
   - `--cwd <path>` — если передан явно (резолвится от process cwd);
   - process current dir — по умолчанию.
3. Для нового запуска CWD выводится в консоль до начала цикла (до выбора
   агента); для resume — сразу после чтения dump.
4. Все относительные пути в `harness.json5` вычисляются относительно CWD.
5. Любой путь из `harness.json5` (относительный или абсолютный) после
   нормализации обязан находиться внутри CWD; иначе — ошибка загрузки.
   Осознанные исключения:
   - `server.tls-cert` / `server.tls-key`;
   - `api-key`-путь в model-файлах;
   - `tools.git.executable` (не является рабочим файлом конфигурации).
6. `--conf <conf>.json5` резолвится от process cwd и обязан находиться
   внутри CWD.

### Dump и возобновление
1. Dump содержит два верхнеуровневых ключа:
   - `"settings"` — конфиг сессии (без `cwd`);
   - `"CWD"` — фактический абсолютный CWD сессии.
2. Новый запуск пишет `"CWD"` при каждом `dump_settings::embed`.
3. Resume запускается как `harness --dump <dump.json5>`:
   - `--dump` — единственный обязательный аргумент;
   - `--cwd` с `--dump` — ошибка CLI;
   - CWD берётся из `"CWD"` в dump, а не из аргументов или process cwd;
   - относительный путь `--dump` резолвится от process cwd.
4. Старые dump-файлы (phase ≤6) не поддерживаются: отсутствие `"CWD"`
   или наличие `cwd` внутри `settings` — ошибка запуска.

### Output buffer
- `output_buff_size` — последний необязательный аргумент `run_shell` и
  `request_command_shell_execution` (default `-1`).
- `-1` — весь вывод; `N >= 0` — последние `N` Unicode-символов вывода.
- Полный вывод по-прежнему стримится в консоль пользователя; ограничение
  касается только строки, возвращаемой агенту.
- `< -1` и нецелые значения — ошибка tool call.

### Deprecated-dir-patterns
- Новый ключ `tools.fs.deprecated-dir-patterns` (массив строк, default `[]`).
- Строгий glob: `**/<component>`, внутри компонента только `*` как wildcard.
- Всё, что вне грамматики, — ошибка конфигурации с указанием позиции
  и доступного синтаксиса.
- Паттерн применяется к нормализованному относительному пути и всем его
  ancestors; на Windows матчинг регистронезависимый, на Unix — регистрозависимый.
- Паттерны валидируются и компилируются в `conf` при загрузке/изменении
  конфигурации, до начала агентского цикла.

### GitHub release action
- Релиз создаётся только для тегов `v*`.
- Версия тега сверяется с `[workspace.package].version`.
- К релизу прикладываются `harness-<version>-windows.exe`,
  `harness-<version>-linux`, `harness-<version>-macos` и их `.sha256`.
- Валидация имён артефактов — строгая (см. решение №5).

## Границы и ограничения
- Консультация не меняет код; далее Project Analyst / Senior Developer
  превращают концепции в задачи разработки.
- Rust-крейты должны оставаться совместимыми с Windows, Linux и macOS.
- `conf` остаётся единственным владельцем чтения json5-конфигов и
  трансляции glob-паттернов.
- Проверка «внутри CWD» — лексическая, по компонентам пути. Симлинки и
  junction'ы не канонизируются: документация не обещает строгую изоляцию
  от выхода через symlink.
- Решения принимаются по принципам KISS и YAGNI.
- Переход на CWD first и новый формат dump — осознанный breaking change
  для конфигов и dump-файлов phase ≤6.
