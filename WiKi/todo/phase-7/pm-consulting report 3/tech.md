# Consulting 3 — Phase 7. Технологии и обоснование

## 1. Общий технологический стек
| Технология | Где используется | Обоснование |
|---|---|---|
| Rust 2021 (workspace) | все крейты | уже принят в проекте; нативная утилита без рантайма |
| `serde_json` | conf, tools, api | работа с JSON-значениями, tool args, dump |
| `json5` | conf, cli-harness | конфиги с комментариями и trailing commas |
| `regex` | tools (уже), conf (добавить) | поиск `find_*_by_regex`; компиляция/валидация `deprecated-dir-patterns` |
| `tokio` + `spawn_blocking` | cli-harness, tools | асинхронный agent loop; блокирующие tool-вызовы вне рантайма |
| `encoding_rs` | tools/process | декодирование OEM/CP1251 вывода shell |
| GitHub Actions | `.github/workflows/ci.yml` | CI/CD уже в проекте |
| `softprops/action-gh-release@v2` | release job | создание GitHub Release без собственного shell-кода |

Новые внешние зависимости: `regex` добавляется только в `conf` (в `tools` он
уже есть). Пакет уже присутствует в `Cargo.lock`, поэтому состав workspace
практически не меняется.

## 2. CWD first — технические решения

### 2.1. Каноническая форма пути
- Все пути приводятся к абсолютному нормализованному виду:
  - `.` — пропускается;
  - `..` — снимает последний компонент;
  - разделители `\` и `/` считаются эквивалентными.
- Проверка «внутри CWD» — по компонентам пути (`starts_with`), а не по строке,
  чтобы `C:\work` не считался внутри `C:\work2`.
- На Windows сравнение компонентов регистронезависимое.

### 2.2. Где применяется резолв
| Источник пути | Старое поведение | Новое поведение |
|---|---|---|
| `cwd` в `harness.json5` | обязательный, от `conf_dir` | запрещён; CWD задаёт запуск |
| `agent.config` | от `conf_dir` | от `cwd`, проверка внутри `cwd` |
| `tools.fs.*` | от `settings.cwd` (из json5) | от `cwd`, проверка внутри `cwd` |
| `tools.terminal.cwd-list` | от `settings.cwd` | от `cwd`, проверка внутри `cwd` |
| `skills.*.file`, `roles.*.file` | от `conf_dir` | от `cwd`, проверка внутри `cwd` |
| `agent.log-folder` | от `cwd` | от `cwd`, проверка внутри `cwd` |
| `--conf` | от process cwd | от process cwd, затем проверка внутри `cwd` |
| `--dump` | от process cwd | от process cwd; CWD берётся из `"CWD"` внутри dump |
| `server.tls-cert` / `tls-key` | строка как есть | отн. от `cwd`, без проверки «внутри» |
| `api-key` в model-файле | отн. от process cwd | отн. от `cwd`, без проверки «внутри» |
| `tools.git.executable` | `Command::new` как есть | без изменений; внешняя команда/файл, не резолвится от CWD |

### 2.3. Почему убираем `cwd` из json5
- `harness.exe` должен запускаться из любого места системы как обычная
  утилита (`PATH`), а рабочая директория должна задаваться местом запуска
  или явным `--cwd`.
- Единственный источник истины для CWD — процесс запуска, а не файл.
- Это убирает неоднозначность: раньше `cwd` зависел от того, где лежит
  конфиг, а не от того, откуда вызван процесс.

### 2.4. Корневая валидация `harness.json5`
- Допустимые корневые ключи: `vars`, `server`, `agent`, `tools`.
- Неизвестный корневой ключ — ошибка загрузки.
- Для ключа `cwd` — отдельное сообщение: `cwd` больше не задаётся в конфиге;
  используйте `--cwd` или запустите процесс из целевой директории.
- Это гарантирует, что `PUT /api/v1/config` с `cwd` в теле вернёт
  `CONFIG_INVALID`, а не молча проигнорирует поле.

### 2.5. Исключения и их обоснование
- **TLS-пути**: относительные резолвятся от CWD, но не обязаны быть внутри
  CWD; сертификаты и ключи часто лежат в системных/пользовательских
  каталогах. CLI-флаги `--tls-cert` / `--tls-key` также вне правила.
- **`api-key`-пути в model-файлах**: относительные резолвятся от CWD,
  абсолютные могут лежать вне CWD; это секрет, а не рабочий файл.
- **`tools.git.executable`**: это исполняемый файл или имя команды, а не
  рабочий файл конфигурации. Значение передаётся в `Command::new` как есть.
  Если в значении нет разделителей пути (например, `"git"`), поиск выполняется
  в `PATH`. Абсолютный путь (`C:\Program Files\Git\cmd\git.exe`) также
  допустим. Никакого резолва от CWD и проверки «внутри CWD» нет.
- Все исключения фиксируются в шаблоне конфига, `help-user.txt` и тестах.

### 2.6. Dump: формат и CWD
- Dump — JSON-объект с верхнеуровневыми ключами:
  - `"settings"` — конфиг сессии (после vars, с абсолютным `agent.config`,
    без `cwd`);
  - `"CWD"` — абсолютный нормализованный CWD сессии.
- `dump_settings::embed(path, settings, cwd)` записывает оба ключа, сохраняя
  vendor-поля dump.
- `dump_settings::extract(path) -> (settings, cwd)` читает оба ключа; dump
  без `"CWD"` или с `cwd` внутри `settings` — ошибка запуска.
- Обратная совместимость со старыми dump-файлами не предусмотрена; старый
  код (`conf_dir_of`) и старую логику удаляем.
- Resume запускается только с `--dump`; `--cwd` с `--dump` — ошибка CLI.

## 3. Output buffer — технические решения

### 3.1. Единица измерения
- Используются **Unicode-символы** (`chars`), а не байты: требование говорит
  о «количестве символов», и это интуитивно для модели.
- Реализация без полного сбора всех символов в `Vec<char>`:
  ```rust
  fn tail_chars(s: &str, n: i64) -> String {
      match n {
          -1 => s.to_string(),
          0 => String::new(),
          _ => s.chars().rev().take(n as usize)
                   .collect::<Vec<_>>().into_iter().rev().collect(),
      }
  }
  ```
  Это ограничивает дополнительную память только `N` последними символами.
- Полный вывод по-прежнему собирается в `run_observed_command` для
  декодирования и стриминга; PO-видимая семантика «буфер вытесняет старые
  значения» обеспечивается возвратом хвоста. Введение bounded ring-buffer на
  этапе чтения — YAGNI для phase-7.

### 3.2. Где обрезать
- Обрезать только строку, возвращаемую агенту. Потоковая печать в консоль
  пользователя остаётся полной — человек видит всё, модель получает хвост.
- Обрезка применяется в `process::run_observed_command` после
  `decode_command_output`, поэтому `terminal` и `user` не дублируют логику.

### 3.3. Валидация аргумента
- `tools::arg_i64(args, key, default)` принимает:
  - JSON-число, представимое в `i64` (не дробное);
  - строку, содержащую целое число;
  - отсутствие/null → `default`.
- Отклоняются bool, object, array, дробные числа и значения вне `i64`.
- Вызывающие модули дополнительно проверяют: `-1` или `>= 0`; иначе — ошибка
  tool call, а не молчаливое трактование как `-1`.

### 3.4. Поведение граничных значений
| `output_buff_size` | Поведение |
|---|---|
| `-1` | весь вывод |
| `0` | пустая строка |
| `N > 0` | последние `N` Unicode-символов |
| `< -1` или нецелое | ошибка tool call |

### 3.5. Schema и совместимость
- `output_buff_size` — `type: "integer"`, опциональный, default `-1`:
  - старые вызовы не ломаются;
  - модель может не передавать его, когда объём не важен.

## 4. Deprecated-dir-patterns — технические решения

### 4.1. Почему glob, а не «сырой» regex
- Примеры PO (`**/log`, `**/done`, `**/note-*`) являются glob-паттернами.
- Сырой Rust `regex` не примет `**/log` без адаптации.
- Трансляция glob → regex проще для конечного пользователя и не требует
  знания regex.

### 4.2. Строгая грамматика (подмножество glob)
- Паттерн обязан иметь вид `**/<component>`.
- `<component>`:
  - непустой;
  - не содержит `/` и `**`;
  - единственный wildcard — `*` (ноль и более символов, кроме `/`).
- Символы `?`, `[`, `]` и прочие regex-метасимволы — **литералы**:
  они экранируются при трансляции и не дают специального поведения.
- Всё, что вне подмножества, — ошибка конфигурации (не «best effort»).
- Допустимые: `**/log`, `**/done`, `**/note-*`, `**/build-*`, `**/log?`.
- Недопустимые: `log/**`, `**/log/**`, `foo/**/bar`, `**`, `**/log/`,
  `**/log/**/x`.

### 4.3. Трансляция (единая функция)
- Единственная реализация — `conf::glob::regex_source(pattern)`.
- Алгоритм:
  1. нормализовать паттерн: `\` → `/`;
  2. на Windows привести паттерн к нижнему регистру;
  3. проверить/снять префикс `**/`;
  4. проверить, что остался ровно один компонент без `/` и без `**`;
  5. в компоненте заменить `*` на `[^/]*`, остальные символы экранировать
     через `regex::escape`;
  6. вернуть `(?:^|/)` + компонентный regex + `(?:/|$)`.
- Примеры:
  | Glob | Regex |
  |------|-------|
  | `**/log` | `(?:^|/)log(?:/|$)` |
  | `**/done` | `(?:^|/)done(?:/|$)` |
  | `**/note-*` | `(?:^|/)note-[^/]*(?:/|$)` |
  | `**/log?` | `(?:^|/)log\?(?:/|$)` |

### 4.4. Сообщения об ошибках валидации
- Ошибка `regex_source` возвращает `ConfError` с текстом вида:
  ```txt
  invalid 'deprecated-dir-patterns' entry '**/log/**':
    unexpected '/' at position 7
    expected pattern '**/<component>'
    only '*' is a wildcard inside <component>; other characters are matched literally
  ```
- Для пустого компонента и `**` внутри компонента — свои конкретные причины.
- Это позволяет пользователю сразу понять, где именно ошибка и как её
  исправить.

### 4.5. Регистронезависимость на Windows
- Механизм: на Windows и паттерн, и проверяемый относительный путь приводятся
  к нижнему регистру до матчинга; сам regex остаётся регистрозависимым.
  Это совпадает с существующей семантикой `comparable_parts` для
  `deprecated-dirs`.
- На Unix приведения регистра нет — матчинг регистрозависимый.
- Покрывается тестами: `**/Log` запрещает `log` на Windows и не запрещает
  `log` на Unix.

### 4.6. Матчинг путей
- Для проверяемого абсолютного пути получить относительный путь от
  `Sandbox.root` в нормализованном виде (слэши `/`, на Windows lowercase).
- Проверить сам относительный путь и все его ancestors:
  - файл `a/log/x.md` → `a`, `a/log`, `a/log/x.md`;
  - директория `a/log` → `a`, `a/log`.
- Если любой из них матчится хотя бы одним паттерном — путь deprecated.

### 4.7. Компиляция и fallible-цепочка
- `conf::load_fs` для каждой строки `deprecated-dir-patterns` вызывает
  `glob::regex_source` и `Regex::new`; ошибка — ошибка загрузки конфига.
- `tools::Sandbox::from_fs` компилирует те же строки той же функцией
  `conf::glob::regex_source` и возвращает `Result`; в штатном сценарии
  ошибка невозможна, так как `conf` уже провалидировал конфиг до начала цикла.
- `ToolRegistry::build` и `FsModule::build` пробрасывают ошибку, а не
  паникуют.

### 4.8. Производительность
- Число паттернов невелико (единицы), компиляция однократная.
- `Regex::is_match` на коротких строках дёшев.
- В `walk_folder` проверка перед рекурсией не допускает обход запрещённых
  поддеревьев.

## 5. GitHub release action — технические решения

### 5.1. Существующий стек
- `actions/checkout@v4`
- `dtolnay/rust-toolchain@stable`
- `actions/upload-artifact@v4` / `actions/download-artifact@v4`
- `softprops/action-gh-release@v2`

Этого достаточно; менять инструменты не требуется.

### 5.2. Доработки
- **Триггер**: release job только для `refs/tags/v*`.
- **Сверка версии**: `tag_version = ${GITHUB_REF_NAME#v}` должен совпадать с
  `[workspace.package].version`.
- **Имена ассетов**:
  - `harness-<version>-windows.exe`;
  - `harness-<version>-linux`;
  - `harness-<version>-macos`.
- **Строгая валидация имени артефакта**:
  `^harness-[0-9]+\.[0-9]+\.[0-9]+(-linux|-macos|\.exe|-windows\.exe)$`.
- **Согласованность upload/download**: Windows-артефакт загружается и
  скачивается под именем `harness-<version>-windows.exe`.
- **Контрольные суммы**: `sha256sum` считается в ubuntu `release` job после
  скачивания артефактов; файлы `release/*.sha256` прикладываются к релизу.
- **Release notes**: `generate_release_notes: true` (нативный механизм GitHub).
- **Проверка полноты**: `Prepare release assets` падает, если любого из трёх
  бинарников нет.
- **Права**: `permissions: contents: write` у release job сохраняется.

### 5.3. Почему не `gh release create`
- `softprops/action-gh-release` уже стоит и покрывает сценарий.
- Меньше shell-кода, декларативная конфигурация, проще поддерживать.
- `gh` CLI имеет смысл, только если понадобится нестандартная логика
  (например, редактирование существующего релиза).

## 6. Риски и ограничения
1. **Изменение семантики CWD ломает существующие конфиги.** Нужно обновить
   `settings-template.json5`, `help.txt`, `help-user.txt` и текущий
   `harness.json5` в корне проекта.
2. **Абсолютные пути вне CWD.** Требование «одна директория — свои конфиги»
   означает, что такие пути — ошибка. Исключения (`tls-cert`, `tls-key`,
   `api-key`, `git.executable`) зафиксированы осознанно.
3. **Симлинки / junction'ы.** Проверка лексическая и не защищает от выхода
   через symlink/junction. Это принятый риск; документация не обещает
   «строгую изоляцию».
4. **Regex-паттерны и Windows.** Регистронезависимость и слэши учитываются
   тестами; механизм — приведение к нижнему регистру на Windows.
5. **Output buffer и Unicode.** Обрезка по символам, а не по байтам, чтобы
   не рвать UTF-8.
6. **Release job зависит от артефактов CI.** Если CI частично упал, релиз не
   должен создаваться; связь `needs: ci` это обеспечивает.
7. **Корневая валидация может выявить старые конфиги с лишними ключами.**
   Это ожидаемое ужесточение; сообщения об ошибках должны быть конкретными.
8. **Новый формат dump — breaking change.** Возобновление старых dump-файлов
   не поддерживается; это осознанное решение PO.
