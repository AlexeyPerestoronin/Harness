# Consulting 3 — Phase 7. REST API

## Область действия
Phase-7 не добавляет новых HTTP-эндпоинтов и не меняет формат существующих
DTO. Изменения касаются **семантики валидации конфигурации** в server-режиме
`harness.exe --serve` и внутренней передачи CWD в загрузчик конфигурации.

## Затрагиваемые эндпоинты

### `GET /api/v1/config`
- Возвращает текущий конфиг.
- Поведение меняется косвенно:
  - в шаблоне/конфиге больше нет поля `cwd`;
  - `valid: true` означает, что конфиг прошёл новую валидацию CWD first
    (все пути внутри CWD, `agent.config` внутри CWD и т.д.);
  - валидация выполняется с CWD сервера, сохранённым в `LoadedServerConfig`.
- Контракт ответа (`path`, `exists`, `text`, `valid`, `validation_error`)
  не меняется.
- `path` в ответе — абсолютный нормализованный путь конфига.

### `PUT /api/v1/config`
- Валидация передаваемого текста использует новую модель CWD:
  - `cwd` в теле конфига **не допускается**: корневая валидация возвращает
    `CONFIG_INVALID` с сообщением, что CWD задаётся только через запуск
    (`--cwd` или process cwd);
  - все относительные пути в конфиге проверяются относительно CWD сервера;
  - пути, выходящие за пределы CWD, отклоняются;
  - `server.tls-cert` / `server.tls-key` остаются исключением из правила
    «внутри CWD»;
  - `tools.git.executable` не проверяется как путь: это внешняя команда
    или исполняемый файл, значение передаётся в `Command::new` как есть.
- CWD сервера передаётся в `validate_config_text` и далее в
  `conf::load_server_config` явно из `state.config.cwd`; process cwd и
  «временный конфиг» не являются источником CWD.
- Сохранение и перезагрузка конфига остаются прежними.
- Сервер стартует с CWD, заданным через `--cwd` или process cwd; через
  `PUT /api/v1/config` изменить CWD невозможно.

### `POST /api/v1/config/default`
- Создаёт `harness.json5` из шаблона, если файл отсутствует.
- Шаблон после phase-7 не содержит `cwd`; поведение эндпоинта не меняется.

## Внутренние изменения server-слоя
- `ServerState` / `LoadedServerConfig` хранит эффективный CWD сервера.
- `LoadedServerConfig.path` — абсолютный нормализованный путь конфига.
- Все вызовы `conf::load_server_config` в `server/config.rs` прокидывают CWD:
  - `get_config`;
  - `config_default`;
  - `validate_config_text`;
  - `read_existing_parsed`;
  - `reload_server_config`;
  - `refresh_server_config`.
- Это закрывает случай, когда конфиг невалиден/отсутствует и `settings == None`,
  но CWD всё равно нужен для повторной валидации и отображения.
- Порядок проверок в `load_server_config`: сначала `ensure_conf_in_cwd`,
  затем чтение/парсинг. Поэтому `--conf` вне CWD при отсутствующем файле
  возвращает ошибку запуска сервера, а не `Missing`.

## Рекомендации
- Отдельные REST-исследования не требуются.
- В `harness-api` (DTO) изменения не нужны.
- В тестах серверного режима добавить кейсы:
  - конфиг с путём вне CWD → `CONFIG_INVALID`;
  - конфиг без `cwd` → валиден;
  - конфиг с `cwd` → `CONFIG_INVALID` (или ошибка старта при явном `--conf`);
  - `--conf` вне CWD → сервер не стартует (даже если файл отсутствует);
  - `PUT /api/v1/config` с относительным путём вне CWD → `CONFIG_INVALID`;
  - `PUT /api/v1/config` с `tools.git.executable: "git"` → валиден;
  - `GET /api/v1/config` возвращает абсолютный `path` и корректный `cwd`.
